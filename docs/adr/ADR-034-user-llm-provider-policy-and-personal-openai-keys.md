# ADR-034: User LLM Provider Policy and Personal OpenAI Keys

## Context

Проект перестал быть чисто single-tenant: бота нужно открывать не только для админов и узкого внутреннего круга, но и для других пользователей.

Текущее состояние слишком грубое для такого сценария:

- доступ к боту хранится только как `allow/deny`;
- весь LLM runtime завязан на глобальный `OPENAI_API_KEY`;
- пользователь не может подключить собственный ключ;
- нельзя отделить доступ к боту от права тратить проектный LLM-бюджет.

При этом согласованы следующие ограничения первого шага:

- админы всегда входят в категорию `internal`;
- обычный пользователь тоже может быть `internal`, если ему поставлена соответствующая отметка;
- пользователь без рабочего ключа всё равно должен иметь доступ к своим записям и аналитике;
- на первом шаге один выбранный provider class используется для всех LLM-сценариев пользователя;
- доступность provider classes задаётся конфигом;
- `Mistral` пока не становится глобальным проектным провайдером;
- первый пользовательский провайдер на реализации - `OpenAI`.

## Decision

### 1. Доступ к боту и доступ к проектному LLM-провайдеру разделяются

`user_access` сохраняется как слой допуска к боту, но дополняется категорией аккаунта:

- `unassigned`;
- `internal`;
- `external`.

Правила:

- админ из `ADMIN_USER_IDS` всегда считается `internal` независимо от строки в таблице;
- обычный пользователь допускается в бот через `is_allowed`;
- категория аккаунта определяет, можно ли использовать проектный провайдер.

### 2. Проектный provider budget доступен только `internal`

Глобальный `OPENAI_API_KEY` проекта остаётся системным ключом только для:

- админов;
- пользователей с категорией `internal`.

Пользователь с категорией `external` не должен случайно использовать проектный ключ даже при наличии доступа к самому боту.

### 3. Для персональных ключей вводится отдельный пользовательский LLM-профиль

В БД появляются отдельные сущности:

- пользовательский `LLM profile`;
- пользовательские `LLM connections`.

Профиль хранит минимум:

- `user_id`;
- `selection_mode`: использовать проектный или персональный источник, если это допустимо.

Подключение хранит минимум:

- `user_id`;
- `provider`;
- `model`;
- зашифрованный `api_key`;
- признаки `is_enabled` и `is_selected`;
- технический статус валидации.

### 4. Секреты пользовательских ключей хранятся в БД в зашифрованном виде

На первом шаге не вводится внешний secret storage.

Вместо этого:

- ключ шифруется перед записью в БД;
- для шифрования используется отдельный application secret из конфигурации;
- БД хранит только ciphertext и технические метаданные.

### 5. Один provider class действует на все LLM-сценарии пользователя

На первом шаге не вводится разная provider policy для:

- extraction;
- nutrition;
- conversation.

Выбранный provider class един для всех трёх сценариев.

При этом конкретная модель внутри provider может различаться по текущей application configuration, поэтому персональные подключения допускается хранить на уровне пары:

- `provider`;
- `model`.

Resolver проверяет подключение отдельно для каждого реально используемого model name.

### 6. Глобальная доступность provider classes задаётся конфигом

Для каждого поддержанного provider class вводится отдельный config flag.

Если provider class выключен конфигом:

- он не используется ни проектным ключом, ни пользовательским ключом;
- resolver обязан отказать до LLM-вызова.

### 7. Админ может выбрать проектный или персональный provider source

Админ остаётся в `internal`, но может:

- использовать проектный ключ;
- переключиться на собственный персональный ключ.

Отдельная специальная политика для временной недоступности персонального провайдера админа не вводится: применяются те же правила отказа, что и для остальных пользователей.

### 8. Пользователь без рабочего ключа сохраняет read-oriented доступ

Если пользователь допущен в бот, но не имеет рабочего LLM-подключения:

- он по-прежнему может смотреть свои записи, цели и аналитические ответы;
- LLM-зависимые сценарии должны отказывать явно и заранее;
- система не должна создавать впечатление, что доступ к данным потерян.

## Consequences

- В модели появляется отдельный слой provider policy, а глобальный LLM key перестаёт быть неявно общим для всех.
- Existing allowed users можно сохранить без регрессии, назначив им `internal` в миграции первого шага.
- Runtime становится сложнее: extraction, nutrition и conversation должны разрешаться не один раз при старте, а с учётом конкретного пользователя.
- Появляется пользовательский контур секретов, поэтому конфигурация deployment теперь должна включать secret для шифрования ключей.
- Первый шаг остаётся обратимым: `OpenAI` поддерживается и как project provider, и как personal provider, а `Mistral` можно добавить отдельным этапом позже без пересмотра базовой модели.
