# ADR-031: Period Report Preferences And Interaction Contract

## Context

В проекте уже есть:

- factual `daily nutrition summary`;
- factual `daily water summary`;
- historical `daily_goal_snapshots`;
- `user_summary_preferences` как отдельный слой пользовательских presentation settings;
- `/today` и post-entry day-report как read-side поверх этих factual summary.

Следующий пользовательский шаг - ввести отдельную команду `/report` с периодной аналитикой.

При этом новый шаг затрагивает сразу несколько разных аспектов:

- новые пользовательские настройки;
- новый read-side contract для period report;
- новый callback/state UX для переключения периода и открытия отдельных детализаций;
- новую интерпретацию `goal hit`, которая больше не должна означать строгое равенство факта и цели.

Важно не смешать этот шаг с отдельными возможными будущими усложнениями:

- не вводить новую materialized period-summary модель до подтверждённой необходимости;
- не превращать `/report` в статистический кабинет со всеми возможными срезами;
- не менять historical goal snapshots задним числом;
- не смешивать presentation preferences с factual metrics пользователя.

## Decision

### 1. Period report остаётся read-side поверх существующих factual summary

`/report` на первом направлении не вводит новый source-of-truth слой.

Он строится как read-side поверх уже существующих сущностей:

- `daily nutrition summary`;
- `daily water summary`;
- `daily_goal_snapshots`;
- factual workout-related данных, если они уже участвуют в текущем summary UX.

На этом шаге не вводятся:

- отдельная таблица period reports;
- materialized aggregates;
- отдельные historical snapshots для period report.

### 2. Period report использует только включённые summary metrics

`/report` и его дочерние детализации показывают только те метрики, которые включены у пользователя в `user_summary_preferences`.

Это правило применяется к:

- основному сообщению `/report`;
- детализации `Заметные записи пищи`;
- детализации `Динамика`.

Если метрика выключена пользователем, она не показывается даже если по ней есть данные.

### 3. В `user_summary_preferences` добавляются две новые report-настройки

В существующую модель `user_summary_preferences` добавляются:

- `report_goal_tolerance_percent`
- `report_noticeable_entry_percentile`

Их смысл:

- `report_goal_tolerance_percent` задаёт допустимое отклонение от цели для period-report блока `Цели`;
- `report_noticeable_entry_percentile` задаёт percentile-порог для отбора заметных записей пищи.

Эти настройки относятся к presentation/analytics contract и не меняют factual data пользователя.

### 4. Значения и диапазоны новых настроек

Для `report_goal_tolerance_percent` поддерживаются фиксированные значения:

- `5`
- `10`
- `15`
- `20`

Значение по умолчанию:

- `10`

Для `report_noticeable_entry_percentile` поддерживаются фиксированные значения:

- `70`
- `75`
- `80`
- `85`
- `90`
- `95`

Значение по умолчанию:

- `80`

На первом шаге обе настройки меняются через `/settings` циклическими кнопками, а не свободным вводом.

### 5. Goal tolerance не снапшотится исторически на этом шаге

Historical `daily_goal_snapshots` продолжают фиксировать только сами goals дня.

Новая настройка `report_goal_tolerance_percent`:

- не записывается в `daily_goal_snapshots`;
- не становится частью historical nutrition fact;
- читается как текущая пользовательская настройка на момент просмотра `/report`.

Следствие:

- одна и та же historical period report может интерпретироваться иначе, если пользователь потом изменит tolerance;
- это считается допустимым на текущем шаге, потому что tolerance является analytics preference, а не factual данными дня.

Если позже появится продуктовая потребность в полной historical reproducibility именно для report-правил, это должно обсуждаться отдельным ADR.

### 6. Goal hit в `/report` считается через диапазон вокруг snapshot goal

Для nutrition и water metrics блок `Цели` в `/report` больше не использует семантику строгого совпадения.

Правило:

- берётся historical goal из `daily_goal_snapshot` соответствующего дня;
- вокруг него строится симметричный допустимый диапазон по `report_goal_tolerance_percent`;
- день считается `in goal`, если factual value попадает в этот диапазон.

Пример:

- `calorie_goal = 1800`
- `report_goal_tolerance_percent = 10`
- допустимый диапазон: `1620-1980`

При этом:

- правила factual aggregation дня не меняются;
- меняется только analytics/read-side интерпретация для period report.

### 7. Defaut `/report` periods фиксируются как 8/16/32 дней

Быстрое переключение периода в `/report` использует только предустановленные периоды:

- `8` дней
- `16` дней
- `32` дня

Причина:

- `Динамика` делит период на подпериоды по `4` дня;
- базовые периоды должны быть кратны этому размеру;
- пользовательский произвольный период на этом направлении не поддерживается.

Default period для `/report`:

- `8` дней

### 8. День с данными по еде определяется по наличию любой food entry

Для period report день считается днём с данными по еде, если в этот день есть хотя бы одна запись еды.

Это правило используется:

- для счётчиков “дней с данными”;
- для средних по еде на уровне периода;
- для подпериодных средних в `Динамике`.

При этом отдельно сохраняется различие между:

- днём с данными по еде;
- полным днём по еде, пригодным для точного nutrition-goal comparison.

### 9. Noticeable entries строятся как верхний хвост по выбранной метрике

Детализация `Заметные записи пищи` не показывает сам percentile как основное содержимое.

User-facing contract:

- пользователь видит список конкретных записей пищи;
- список строится по одной метрике за раз;
- доступные метрики ограничены включёнными у пользователя и реально имеющими записи в периоде;
- показывается не больше `10` записей;
- у каждой записи обязательно показывается дата.

Internal rule:

- `report_noticeable_entry_percentile` задаёт порог по выбранной метрике;
- в список попадают записи из верхнего хвоста распределения относительно этого порога.

На этом шаге percentile считается внутренней технической логикой отбора, а не обязательным термином интерфейса.

### 10. Динамика строится отдельным сообщением по подпериодам 4 дня

Детализация `Динамика`:

- открывается отдельной кнопкой из основного `/report`;
- рендерится отдельным сообщением;
- показывает одну метрику за раз;
- использует те же ограничения по доступным метрикам, что и остальные report-детализации.

Период делится на подпериоды по `4` календарных дня:

- подпериоды показываются в хронологическом порядке;
- для каждого подпериода выводится среднее по дням с данными внутри подпериода;
- если данные есть, рядом выводится `(N/4 дней)`;
- если данных нет, подпериод всё равно остаётся в списке и показывает `нет данных`.

### 11. Для `/report` вводится отдельный callback/state contract

UX period report не должен строиться ad hoc поверх существующих callback-структур.

Нужен отдельный callback/state contract как минимум для:

- циклического переключения периода в основном сообщении `/report`;
- открытия детализации `Заметные записи пищи`;
- циклического переключения метрики внутри `Заметных записей пищи`;
- открытия детализации `Динамика`;
- циклического переключения метрики внутри `Динамики`;
- удаления дочерних report-сообщений по кнопке `Закрыть`;
- удаления основного report-сообщения по отдельной кнопке.

На этом шаге считается допустимым:

- хранить нужный report context в callback payload, если он остаётся компактным;
- либо использовать отдельную техническую state-модель, если callback payload становится избыточным.

Но сами callback ids и обработчики должны оставаться изолированными от уже существующих settings/files/recent flows.

### 12. `/settings` расширяется как единая точка управления report-настройками

Новые настройки:

- `report_goal_tolerance_percent`
- `report_noticeable_entry_percentile`

добавляются в уже существующий `/settings`.

При этом допустимо:

- изменить порядок кнопок;
- изменить форму текущей мозаики;
- перегруппировать summary-related settings,

если это делает UX понятнее и не смешивает report preferences с unrelated admin или journaling flows.

## Consequences

- `/report` получает отдельный и достаточно узкий аналитический contract без новой period-summary модели.
- `user_summary_preferences` остаётся единым местом для display и analytics preferences пользователя.
- Historical goals продолжают храниться отдельно от текущих report preferences, что сохраняет обратимость шага.
- Появляется явная граница между factual day aggregation и report-specific analytics interpretation.
- Реализация `/report` получает собственный callback/state boundary и не размывает уже существующие Telegram flows.
