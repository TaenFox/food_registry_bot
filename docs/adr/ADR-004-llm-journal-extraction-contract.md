# ADR-004: LLM Journal Extraction Contract

## Context

Проект уже умеет сохранять простые записи еды и воды, а также принимать нормализованный JSON с несколькими `entries` в одном сообщении. Следующий целостный шаг - отделить будущий LLM extraction layer от Telegram-обработчика и зафиксировать первый контракт структурированного результата.

Нужно определить:

- какую минимальную структуру обязана возвращать LLM;
- какие поля обязательны на первом шаге;
- как в одном сообщении поддерживаются несколько записей и сочетание еды с водой;
- где проходит граница между обязанностями LLM и нормализацией в приложении.

При этом в этом шаге не нужно:

- выбирать боевого LLM-провайдера;
- проектировать prompt engineering и retry-инфраструктуру;
- разбирать свободный текст rule-based логикой.

## Decision

### 1. Контракт extraction result

На первом шаге extraction layer возвращает JSON-объект вида:

```json
{
  "entries": [
    {
      "type": "food",
      "items": [
        {"name": "гречка", "quantity": 200, "unit": "г"},
        {"name": "курица", "quantity": 150, "unit": "г"}
      ]
    },
    {
      "type": "water",
      "items": [
        {"name": "вода", "quantity": 250, "unit": "мл"}
      ]
    }
  ]
}
```

Корневой объект обязан содержать непустой массив `entries`.

### 2. Обязательные поля

Для каждого `entry` обязательны:

- `type` - тип записи журнала; на этом шаге поддерживаются `food` и `water`;
- `items` - непустой массив позиций, относящихся к этой записи.

Для каждого `item` обязательно:

- `name` - непустое название позиции.

### 3. Опциональные поля первого шага

На первом шаге разрешены, но не обязательны:

- `entry.occurred_at` - timestamp события в ISO 8601, если он явно извлекается из сообщения;
- `item.quantity` - целое положительное количество;
- `item.unit` - единица измерения, если указано `quantity`.

Если `quantity` и `unit` всё же возвращаются, extraction layer должен по возможности использовать базовые единицы текущего шага:

- для еды - в первую очередь `г`, а для жидких food items вроде соусов допустимо `мл`;
- для воды и напитков - `мл`.

Единицы вроде `порция`, `штука`, `кусок`, `ложка` и похожие расплывчатые значения на этом шаге нежелательны. Если уверенной оценки нет, лучше не возвращать `quantity` и `unit` вовсе.

`meal_type`, метрики, confidence-оценки, объяснения, ссылки на исходные фрагменты сообщения и любые другие поля в этот контракт пока не включаются.

### 4. Несколько entries в одном сообщении

- Один пользовательский input может приводить к нескольким `entries`.
- Каждый элемент массива `entries` создаёт отдельную запись журнала.
- Если в одном сообщении есть и еда, и вода, они должны возвращаться как разные `entries`, а не смешиваться в одной записи.
- Несколько `items` внутри одного `entry` используются для позиций одного и того же события журнала, например нескольких продуктов в одной записи еды.

### 5. Граница ответственности

LLM обязана:

- вернуть JSON строго по контракту без дополнительного свободного текста;
- выбрать корректный `entry.type` для каждой записи;
- сгруппировать позиции по отдельным `entries`;
- передать непустые `items` и непустые `name`;
- передать `occurred_at`, только если она действительно извлекла время события.

Приложение обязано:

- валидировать структуру и типы полей;
- отклонять payload с неизвестными полями;
- нормализовать допустимые синонимы воды и базовых единиц измерения, например `вода` -> `water`, `мл` -> `ml`, `г` -> `g`;
- по возможности детерминированно переводить типовые бытовые food-единицы вроде `стакан` или `шт` в базовые `ml`/`g`, если для этого есть простой и наблюдаемый сценарий;
- подставлять `occurred_at = now()` при отсутствии времени в payload;
- преобразовывать валидный extraction result в доменные записи и сохранять их в БД.

Невалидным ответом LLM считается любой payload, в котором:

- отсутствует корневой объект `{"entries": [...]}`;
- `entries` пустой;
- у `entry` нет `type` или `items`;
- `items` пустой;
- у `item` нет `name`;
- `quantity` не является положительным целым числом;
- указан `unit`, но отсутствует `quantity`;
- присутствуют неизвестные поля;
- JSON повреждён или дополнен произвольным текстом.

### 6. Техническая граница слоя

В приложении вводится отдельный extraction boundary:

- schema / Pydantic models для extraction contract;
- интерфейс extraction service;
- временная dev-заглушка, которая принимает structured payload в том же контракте.

Эта заглушка нужна только для инкрементальной сборки слоя и тестов. Она не является product-level parser для свободного текста.

## Consequences

- Контракт LLM extraction фиксируется отдельно от Telegram handler и может независимо развиваться дальше.
- Следующий шаг можно делать поверх явной service boundary, а не поверх ad hoc JSON-парсинга в обработчике.
- Свободный текст пока по-прежнему сохраняется минимальной food-записью, пока не появится реальная extraction integration.
- Контракт остаётся узким и обратимым: без premature design для метрик, meal type, retries и провайдерской инфраструктуры.
