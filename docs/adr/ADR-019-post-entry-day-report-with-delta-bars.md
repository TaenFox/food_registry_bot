# ADR-019: Post-Entry Day Report With Delta Bars

## Context

В системе уже есть:

- дневной factual summary по еде;
- отдельный дневной factual summary по воде;
- goals и daily snapshots;
- `/today`, который умеет `text` и `bars`.

Следующий шаг - сделать confirmation после записи симметричным `/today`, чтобы пользователь сразу видел новый итог пищевого дня и вклад только что добавленной записи.

## Decision

### 1. Confirmation after write

После успешной записи еды или воды бот отвечает не отдельным кратким итогом по сообщению, а:

- блоком `Сохранил:`
- и затем тем же day-report, который используется в `/today`

Это означает, что confirmation строится поверх:

- того же `timezone`;
- того же `nutrition_day_start_hour`;
- того же factual summary layer;
- того же goal snapshot для текущего пищевого дня.

### 2. Delta rendering

Confirmation дополнительно знает вклад только что сохранённой записи.

Для этого в rendering передаётся `metric delta` по затронутым показателям.

### 3. Поведение в `text` mode

Если у пользователя `summary_display_mode = text`, confirmation использует тот же формат, что и `/today`, но у изменившихся строк добавляет суффикс:

- `(+delta)`

Например:

- `К: 540.0 / 1800 ккал (+220.0)`
- `В: 750.0 / 2000 мл (+250.0)`

### 4. Поведение в `bars` mode

Если у пользователя `summary_display_mode = bars`, confirmation использует ту же 10-символьную шкалу, что и `/today`, но:

- `█` означает объём, который был до новой записи;
- `▓` означает объём, добавленный текущей записью;
- `░` означает оставшуюся часть до цели.

Если цель превышена:

- уже превышенная часть справа от `]` рисуется `█`;
- новое превышение справа от `]` рисуется `▓`.

### 5. Scope шага

Delta confirmation применяется к уже поддержанным показателям:

- `calories`
- `protein`
- `fat`
- `carbs`
- `water`

Если одно сообщение затрагивает несколько разных пищевых дней, confirmation не пытается синтезировать единый day-report и остаётся только с блоком `Сохранил:`.

## Consequences

- Confirmation после записи и `/today` используют единый read-side contract.
- Пользователь сразу видит не только то, что запись сохранена, но и как она изменила дневной итог.
- Следующие UX-шаги можно развивать без изменения snapshot/factual model, только поверх rendering contract.
