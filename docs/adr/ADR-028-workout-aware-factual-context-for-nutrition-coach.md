# ADR-028: Workout-Aware Factual Context for Nutrition Coach

## Context

В проекте уже реализован первый factual workout layer:

- тренировки сохраняются как `entry_type = workout`;
- workout logging включается пользователем отдельно;
- `/today` уже может показывать список тренировок при включённой workout-функциональности.

Следующий целостный шаг - начать использовать эти workout facts внутри `nutrition coach`.

При этом важно не смешать в одном этапе несколько разных направлений:

- не вводить отдельный `trainer coach`;
- не менять goals и goal snapshots;
- не строить расчётный workout expenditure;
- не потерять уже известные workout facts при дальнейшем расширении модели.

Отдельно в обсуждении зафиксировано:

- в factual context лучше передавать все известные системе факты о тренировке, а не только часть из них;
- тренировочный context лучше передавать всегда, а не только по эвристике релевантности;
- `nutrition coach` может использовать расширенный режим интерпретации, но должен опираться только на факты, реально присутствующие в системе;
- goals, связанные с тренировками, не рассматриваются как ожидаемое направление продукта на текущем этапе.

## Decision

### 1. Nutrition coach получает workout context всегда

Если у пользователя включена workout-функциональность, `nutrition coach` всегда получает workout-related factual context текущего nutrition-day.

Это правило не зависит от темы конкретного вопроса.

Причина:

- факт тренировки может быть важен даже для обычного вопроса про ужин, воду или добор белка;
- решение о релевантности лучше оставить самому coach prompt, чем заранее резать context эвристикой.

### 2. В coach context передаются все известные workout facts текущей модели

Workout context должен содержать не только “сегодня была тренировка”, а все факты, которые уже известны и сохранены системой для конкретной workout entry.

На текущем этапе это включает как минимум:

- `entry_id`;
- `occurred_at`;
- `source_text`, если он сохранён;
- `items` тренировки:
  - `name`;
  - `quantity`;
  - `unit`.

Если позже в workout layer появятся новые factual поля или сохранённые workout metrics, они должны расширять этот context, а не подменять его более узкой производной формой.

### 3. Coach может использовать расширенную nutrition-интерпретацию, но только поверх фактов

`nutrition coach` разрешается учитывать workout context в расширенном режиме ответа, например:

- при рекомендациях по приёму пищи после тренировки;
- при ответах про белок, углеводы, hydration и timing питания;
- при объяснении, как лучше завершить день питания с учётом уже состоявшейся нагрузки.

При этом coach не должен:

- придумывать отсутствующие workout facts;
- заявлять расчётный расход калорий, если он не сохранён как факт;
- выдавать псевдоточные выводы про intensity, recovery cost или load score, если таких factual данных в системе нет.

### 4. Workout-aware coach не становится trainer coach

На этом этапе `nutrition coach` остаётся nutrition-first агентом.

Workout context используется только как дополнительный factual слой для nutrition guidance.

Это означает:

- советы по еде и воде вокруг тренировки допустимы;
- интерпретация влияния уже случившейся тренировки на питание дня допустима;
- построение тренировочных программ, periodization и coaching по выполнению упражнений в этот этап не входят.

### 5. Goals и snapshots тренировками не меняются

Workout-aware factual context на этом этапе:

- не меняет `daily goals`;
- не меняет `daily goal snapshots`;
- не вводит workout-specific goal model;
- не добавляет “цели по тренировкам” как новый продуктовый слой.

Если когда-либо появится отдельная продуктовая потребность в workout goals или workout-derived goal adjustments, это должно обсуждаться отдельно, а не как продолжение текущего ADR.

### 6. Contract строится расширяемым к будущим factual workout metrics

Хотя на текущем шаге система ещё не хранит factual calories burned и другие workout metrics как отдельный слой, coach context должен проектироваться так, чтобы позже их можно было добавить без пересмотра boundary.

Следствие:

- workout context лучше хранить как структурированный список workout entries;
- каждая entry должна допускать последующее расширение factual fields;
- будущие сохранённые workout metrics, например factual calories burned из tracker app, должны добавляться как новые factual поля контекста, а не вычисляться задним числом эвристикой внутри coach.

## Consequences

- `nutrition coach` начинает учитывать реальную тренировочную нагрузку дня там, где это полезно для питания и воды.
- Context builder становится богаче, но не требует отдельной workout analytics модели.
- Проект сохраняет расширяемость к будущим factual workout metrics без ранней фиксации на расчётной модели расхода.
- Направление с workout goals явно не считается текущим ожидаемым развитием продукта.
