# ADR-027: Opt-In Text Workout Logging on Unified Journal

## Context

В проекте уже зафиксировано, что тренировки должны жить внутри общей journal-модели как `entry_type = workout`, а не как отдельная подсистема.

При этом первый практический шаг должен оставаться небольшим и проверяемым:

- не вводить полноценную фитнес-модель;
- не добавлять screenshot parsing;
- не смешивать в одном инкременте workout logging и workout-based goal adjustments;
- не менять поведение для пользователей, которым тренировки не нужны.

Отдельно было согласовано, что workout-функциональность должна быть пользовательской опцией и по умолчанию оставаться выключенной.

## Decision

### 1. Workout logging вводится как opt-in пользовательская функция

- У пользователя появляется флаг `workout_logging_enabled`.
- Флаг хранится в основной сущности `users`.
- Значение по умолчанию: `false`.
- Пока пользователь явно не включил workout logging, система не должна сохранять workout entries.

### 2. Первый шаг поддерживает только text-first workout logging

В первый этап входят только текстовые workout journal messages.

Примеры целевого пользовательского ввода:

- `тренировка: бег 40 минут`;
- `сегодня была силовая 50 минут`;
- `велотренажёр 30 минут`.

Поддержка workout screenshots в этот ADR не входит.

### 3. Workout logging остаётся частью unified journal

- Тренировка сохраняется как обычный `entry`.
- `entry.entry_type = workout`.
- Сохраняется `source_text` исходного пользовательского сообщения.
- Дополнительная workout-таблица на этом шаге не вводится.

### 4. Первый structured workout contract остаётся минимальным

Первый structured contract для workout entry использует уже существующую модель `entry_items`:

- `entry.type = workout`;
- `items` содержит хотя бы один workout item;
- `item.name` хранит название тренировки или активности;
- `item.quantity` и `item.unit` опционально используются только для длительности;
- если длительность указана, `unit = min`.

На этом шаге:

- поддерживаются только `min` или отсутствие единицы;
- дистанция, темп, пульс, нагрузка, калории тренировки и другие детали не нормализуются в отдельные поля;
- такие детали могут остаться только в `source_text` до следующего этапа модели.

### 5. Routing для workout journal делается консервативным

Система должна различать:

- nutrition-вопросы про тренировку;
- явные workout journal messages.

Правило первого шага:

- явные journal cues тренировок имеют приоритет над общими conversational cues;
- вопросительные и явно advisory сообщения остаются в `conversation`;
- если намерение недостаточно ясно, сообщение не должно молча сохраняться как workout fact.

### 6. Поведение при выключенной workout-функции

Если extraction распознала `workout` entry, но у пользователя `workout_logging_enabled = false`:

- запись не сохраняется;
- бот возвращает прозрачный ответ, что функциональность тренировок выключена;
- бот подсказывает включить её через `/settings`.

### 7. Summary и goals на этом шаге не меняются

На первом этапе workout entries:

- не включаются в nutrition summary;
- не меняют daily goals;
- не меняют daily goal snapshots;
- не создают отдельный workout summary contract.

Подтверждение после успешной записи тренировки не должно подставлять misleading nutrition summary, если в сообщении не было food/water entries.

## Consequences

- Появляется первый рабочий workout fact layer без новой сложной схемы.
- Пользовательский rollout остаётся безопасным за счёт opt-in поведения.
- Система получает базу для следующих шагов: workout-aware nutrition context и позже workout impact on goals.
- Первый слой намеренно ограничен: часть workout-деталей временно живёт только в `source_text`, чтобы не переусложнять модель раньше времени.
