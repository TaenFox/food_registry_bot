# ADR-035: Diet Tracking With Item-Level Scores

## Context

Проект уже поддерживает:

- item-level хранение nutrition metrics через `supported_metrics` и `entry_item_metrics`;
- отдельный post-entry comment в `entries.llm_comment`;
- `/settings` как слой пользовательских presentation/preferences настроек;
- `/recent` с entry-level и item-level navigation;
- `/report`, который умеет честно работать с неполными историческими данными.

Новый шаг - добавить сопровождение диет так, чтобы:

- в первой реальной версии была поддержана конкретная диета `низкопуриновая`;
- новые диеты можно было добавлять без пересмотра базовой модели;
- оценка диеты относилась к отдельному блюду, а не ко всей записи;
- вода тоже могла учитываться как полезный item для конкретной диеты;
- старые записи без diet-оценки не требовали обязательного backfill;
- существующий post-entry comment учитывал включённые диеты пользователя;
- новая функциональность не превращала diet score в новую систему целей.

При этом уже согласованы следующие продуктовые ограничения:

- пользователь может включать каждую поддержанную диету отдельно;
- первая реализация использует только LLM для diet evaluation;
- после включения диеты оцениваются только новые записи;
- в `/recent` показывается средний diet score по приёму пищи, но не item-level score на экране блюда;
- в `/report` достаточно общей пометки о неполных diet-данных;
- в conversational LLM context должна передаваться информация о включённых диетах пользователя.

## Decision

### 1. Первая обязательная диета - `низкопуриновая`

На первом шаге проект не ограничивается абстрактной инфраструктурой под будущие диеты.

Обязательная первая диета:

- `низкопуриновая`.

При этом модель проектируется расширяемой к следующим diet codes без пересмотра базовых сущностей.

### 2. Поддержанные диеты задаются отдельным developer-managed справочником

В БД вводится отдельный справочник поддержанных диет:

- `supported_diets`.

Минимально он хранит:

- `code`;
- `name`;
- `is_enabled`.

Дополнительная prompt/rubric-конфигурация может жить либо в коде, либо в справочнике, но code диеты должен быть стабильным и использоваться:

- в пользовательских настройках;
- в naming diet metric codes;
- в runtime-логике evaluation.

Пользователь не создаёт свои произвольные диеты.

### 3. Пользовательские настройки диет хранятся отдельно от summary metric visibility

Включение диет не считается обычным toggle показа summary metrics.

Для этого вводится отдельный пользовательский слой настроек diet tracking.

На первом шаге допустима реализация одним из двух технических вариантов:

- отдельные поля в `user_summary_preferences`;
- отдельная таблица пользовательских diet preferences.

Архитектурное решение фиксируется так:

- настройки должны выражать независимое включение каждой поддержанной диеты;
- модель не должна навязывать единственную активную диету;
- переключение диеты не должно переписывать исторические данные.

### 4. Diet score хранится как item-level metric в существующем metric storage

Diet score не получает отдельную таблицу значений.

Вместо этого:

- для каждой поддержанной диеты добавляется отдельный developer-managed metric code в `supported_metrics`;
- значения сохраняются в существующем `entry_item_metrics`.

Для первой версии добавляется как минимум:

- `low_purine_score`.

Правила:

- оценка относится к конкретному `entry_item`;
- один `entry_item` может иметь несколько diet scores для разных диет;
- diet metrics не становятся частью `user_goal_preferences`;
- diet metrics не попадают в `daily_goal_snapshots`.

### 5. Water entries тоже получают diet score

Вода не исключается из diet tracking.

Так как вода уже хранится как item внутри water entry:

- diet score для воды сохраняется тем же item-level способом через `entry_item_metrics`.

Для `низкопуриновой` диеты фиксируется пользовательское правило:

- вода считается полезным приёмом и должна улучшать средний бал.
- конкретное значение для воды задаётся в коде диеты, не вычисляется через LLM и может быть высоким, но не максимальным.

### 6. Diet evaluation использует смешанный подход: LLM для еды, фиксированные правила для воды

На первом шаге не вводится общий rule-based evaluator для еды.

Вместо этого:

- `food items` получают diet score через LLM;
- `water items` получают заранее заданное per-diet значение из registry поддержанных диет.

Diet evaluation выполняется отдельным runtime-слоем, например `DietEvaluationService`, который:

- получает сохранённые `entry_item`;
- учитывает включённые диеты пользователя;
- вызывает LLM;
- сохраняет item-level diet scores.

Если позже появится потребность в rule-based логике, это должно обсуждаться отдельным ADR.

### 7. Post-entry comment остаётся единым и становится diet-aware

Не вводится второй параллельный comment layer для диет.

Существующий post-entry comment:

- по-прежнему хранится в `entries.llm_comment`;
- по-прежнему относится к successful food write flow;
- расширяется так, чтобы учитывать включённые диеты пользователя.

Дополнительно фиксируется:

- пользовательский префикс `Нутрициолог` убирается из рендера comment;
- comment остаётся одним коротким текстом;
- comment generation по-прежнему не должна откатывать сохранение записи при ошибке.

### 8. Conversational context тоже становится diet-aware

Diet support относится не только к write flow.

Nutrition coach в режиме диалога тоже должен получать информацию о включённых диетах пользователя.

Для этого conversational context расширяется данными о диетах:

- список включённых diet codes;
- display names включённых диет.

Эти данные:

- передаются в LLM вместе с factual day context;
- используются как пользовательские ограничения при ответах про выбор еды, планирование и воду;
- не подменяют factual day data и не считаются nutrition metrics.

### 9. Исторические записи без diet score допустимы

После включения диеты обязательный backfill старых записей не выполняется.

Правило первого шага:

- diet scores появляются только у новых записей после включения диеты;
- старые записи без diet scores считаются допустимым неполным историческим состоянием.

Read-side должен использовать ту же общую семантику, что уже есть у nutrition-агрегаций:

- отсутствие нужной метрики не считается повреждением данных;
- агрегаты считаются только по тем сущностям, где нужная метрика присутствует;
- пользователю можно показывать общую пометку о неполных данных.

### 10. `/recent` показывает только entry-level средний diet score

`/recent` не становится экраном подробной диетической аналитики по блюдам.

Правило:

- в списке recent entries и на entry-level экране можно показывать средний diet score по приёму пищи;
- при переходе к конкретному блюду item-level diet score не показывается.

Средний score записи строится как агрегат по item-level diet metrics этой записи.

### 11. `/report` показывает diet score отдельно от goal-oriented metrics

Diet scores не участвуют в блоке целей.

В `/report` diet layer:

- показывается отдельным блоком;
- считается по item-level diet metrics;
- показывает средневзвешенный по `quantity` score по оценённым блюдам;
- показывает количество блюд и дней, вошедших в расчёт;
- может сопровождаться общей пометкой о неполных diet-данных.

## Consequences

- Первая версия получает реальную поддержку `низкопуриновой` диеты, а не только подготовку инфраструктуры.
- Item-level diet scores ложатся в уже существующую metric model без отдельной таблицы значений.
- Вода естественно встраивается в diet tracking, потому что уже хранится как item.
- Старые записи без diet scores не ломают модель и не требуют обязательного backfill.
- Post-entry feedback остаётся единым для пользователя, но становится diet-aware.
- Conversational reply тоже становится diet-aware за счёт расширения context, а не отдельного ad hoc prompt state.
- В `/recent` и `/report` появляется новый read-side слой, который можно реализовать поверх уже существующих entry/item и period-aggregation сценариев.
