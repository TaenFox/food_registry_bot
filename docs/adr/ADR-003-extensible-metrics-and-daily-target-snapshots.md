# ADR-003: Extensible Metrics and Daily Target Snapshots

## Context

Проект должен отслеживать не только калории и БЖУ, но и дополнительные показатели, например клетчатку, воду и пуриновый риск. В будущем могут появиться и другие поддерживаемые метрики.

При этом:

- пользователь не должен создавать произвольные новые метрики сам;
- пользователь должен иметь возможность выбирать, какие из поддержанных метрик ему показывать;
- исторические отчёты не должны менять смысл после изменения текущих пользовательских настроек;
- дневные цели могут корректироваться, например, на основе тренировок.

Если жёстко зашить все показатели в основную таблицу записей, это ухудшит расширяемость. Если же вычислять цели дня только из текущего состояния профиля, исторические данные начнут плыть.

## Decision

- Поддерживаемые метрики определяются разработчиком в коде и сопровождаются миграциями и доменной логикой.
- Пользователь может настраивать только включение и отключение уже поддержанных системой метрик.
- Значения метрик хранятся отдельно от базовых сущностей записей и позиций записей.
- Для метрик должен существовать справочник определений, описывающий код, тип значения, единицу измерения, уровень применения и правила агрегации.
- Дневные цели пользователя фиксируются как снимок настроек на конкретную дату.
- Корректировки, связанные с тренировками или другими событиями дня, применяются к цели конкретного дня, не меняя исторические цели прошлых дней.

## Consequences

- Система может расширяться новыми поддерживаемыми метриками без пересмотра основной модели журнала.
- Пользовательская персонализация ограничивается безопасным и контролируемым уровнем: выбором из уже поддержанных метрик.
- Исторические дневные отчёты сохраняют корректный смысл даже после изменения настроек профиля.
- Для логики отчётов и агрегаций потребуется отдельный слой работы с определениями метрик и дневными целями.
- Модель становится немного сложнее, чем фиксированный набор колонок, но лучше соответствует долгосрочным требованиям проекта.
