# ADR-009: Entry Item Metric Storage for Nutrition Estimates

## Context

Nutrition estimation contract уже выделен в отдельный слой и на первом шаге возвращает item-level result с метриками `calories`, `protein`, `fat` и `carbs`, а также с `confidence` на уровне каждой метрики.

Следующий шаг - сохранить эти результаты в БД так, чтобы решение:

- не смешивало nutrition estimates с базовой journal model;
- поддерживало несколько метрик на один `entry_item`;
- не зашивало текущий набор метрик в фиксированные колонки;
- позволяло в будущем добавлять новые поддерживаемые метрики через код и миграции.

При этом на этом шаге не нужно:

- хранить историю версий одной и той же оценки;
- строить дневные агрегаты;
- вводить пользовательский UI для nutrition explanation;
- сохранять отдельный nutrition trace payload, если для него ещё нет практического сценария.

## Decision

### 1. Метрики хранятся отдельно от `entry_items`

Для хранения nutrition estimates вводятся две таблицы:

- `supported_metrics` - справочник поддерживаемых системой метрик;
- `entry_item_metrics` - текущее значение конкретной метрики для конкретного `entry_item`.

### 2. Справочник поддерживаемых метрик

На первом шаге `supported_metrics` содержит только:

- `calories`;
- `protein`;
- `fat`;
- `carbs`.

Каждая метрика определяется разработчиком и добавляется миграцией. Пользователь не создаёт собственные метрики.

### 3. Хранение значений

Каждое значение метрики хранится как отдельная запись вида:

- `entry_item_id`;
- `metric_id`;
- `value`;
- `confidence`.

Это означает:

- один `entry_item` может иметь несколько записей метрик;
- для каждой пары `(entry_item_id, metric_id)` хранится только одно текущее значение;
- повторная переоценка обновляет и значение, и confidence, а не создаёт новую версию.

Для этого на `entry_item_metrics` вводится уникальность по `(entry_item_id, metric_id)`.

### 4. Уровень применения

На этом шаге nutrition estimates сохраняются только на `item-level`.

Не вводятся:

- `entry-level` nutrition rows;
- дневные nutrition rows;
- version history;
- nutrition raw trace tables.

### 5. Trace на этом шаге

Отдельное хранение `nutrition_provider`, `nutrition_model` и `raw_payload` в БД пока не добавляется.

Причины:

- пока нет пользовательского сценария пересчётов и сравнения качества nutrition provider;
- текущий шаг должен остаться минимальным;
- если позже появится потребность в наблюдаемости, nutrition trace можно будет ввести отдельной сущностью или отдельными полями без ломки основной модели значений метрик.

## Consequences

- Модель БД остаётся совместимой с ADR-003 про расширяемые поддерживаемые метрики.
- Nutrition estimates сохраняются отдельно от базовых journal entities и не раздувают `entry_items` фиксированными колонками.
- Повторная переоценка работает как обновление текущего состояния, а не как журнал версий.
- Если позже понадобятся version history, provider trace или агрегированные уровни хранения, это будет отдельным расширением поверх текущей схемы.
