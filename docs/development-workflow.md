# Development Workflow

## Назначение

Этот документ фиксирует рабочий процесс разработки, правила работы с ветками и порядок подготовки релиза в проекте `food_registry_bot`.

## Ветки

В проекте используются две долго живущие ветки:

- `main`
- `develop`

### Роли веток

- `main` содержит состояние, соответствующее готовому релизу.
- `develop` является основной веткой интеграции текущей разработки.
- повседневная разработка не ведётся напрямую ни в `main`, ни в `develop`.

### Защита ветки `main`

Для ветки `main` в GitHub должен быть включён branch protection rule или ruleset.

Минимальное ожидаемое поведение этой защиты:

- прямой push в `main` запрещён;
- изменение `main` выполняется только через pull request;
- merge commit'ы в `main` не допускаются, если для ветки включена linear history;
- удаление `main` запрещено без отдельного bypass-права.

## Рабочие деревья

В проекте используется одно основное интеграционное рабочее дерево и несколько дополнительных агентских рабочих деревьев.

### Основное рабочее дерево

Основное рабочее дерево используется как точка review, merge и интеграции.

Пример имени:

`food_registry_bot`

Правила:

- имя основного рабочего дерева должно содержать префикс имени проекта;
- основное рабочее дерево по умолчанию работает на ветке `develop`;
- в основном рабочем дереве не ведётся обычная разработка задач;
- основное рабочее дерево используется для review изменений, merge веток в `develop`, интеграционных проверок и подготовки релиза;
- переключение основного рабочего дерева на `main` допускается только для релиза, review релизного состояния или hotfix-проверки.

### Агентские рабочие деревья

Дополнительные рабочие деревья создаются как постоянные слоты для работы агентов.

Примеры имён:

- `food_registry_bot__codex-1`
- `food_registry_bot__codex-2`
- `food_registry_bot__claude-1`

Правила:

- имя агентского рабочего дерева должно содержать префикс имени проекта;
- одно агентское рабочее дерево соответствует одному агентскому слоту;
- в каждый момент времени агентское рабочее дерево должно содержать одну активную рабочую ветку;
- агентское рабочее дерево может переиспользоваться для следующих задач после завершения предыдущего цикла работы.

## Рабочие ветки

Правила:

- одна рабочая ветка соответствует одной логической задаче или доработке;
- для именования рабочих веток следует использовать префикс `task/`;
- прямую разработку в `main` и `develop` следует избегать.

Пример имени ветки:

`task/add-entry-model`

Имя ветки должно отражать смысл задачи, а не имя агента или модели. Агент может меняться по ходу работы без необходимости переименовывать ветку.

## Создание новой рабочей ветки

Новая рабочая ветка может создаваться:

- либо от `develop`;
- либо от текущей ветки агентского рабочего дерева.

При этом действуют правила:

- если новая ветка создаётся от `develop`, должен использоваться актуальный `develop`;
- если новая ветка создаётся от текущей ветки агентского рабочего дерева, в эту базовую ветку сначала должен быть влит актуальный `develop`;
- новая ветка не должна начинаться от устаревшего состояния относительно `develop`.

Смысл правила в том, что база новой ветки должна быть синхронизирована с актуальной интеграционной историей `develop`.

## Жизненный цикл задачи

1. Убедиться, что задача не зависит от ещё не реализованной базовой функциональности.
2. Если зависимость есть, явно обозначить её и не начинать реализацию, пока не согласован или не выполнен необходимый базовый этап.
3. Подготовить агентское рабочее дерево и создать в нём рабочую ветку.
4. Выполнить изменение короткими инкрементами, сохраняя проект в проверяемом состоянии.
5. Если изменение затрагивает доменную модель, схему БД или архитектурное решение, проверить необходимость нового ADR.
6. Обновить документацию, если изменились сценарии, ограничения или инженерные договорённости.
7. Перед финализацией влить в рабочую ветку актуальный `develop`, разрешить конфликты и заново прогнать необходимые проверки.
8. По запросу на финализацию изменений выполнить merge рабочей ветки обратно в `develop`.

## Работа внутри агентского рабочего дерева

Внутри агентского рабочего дерева допускается вести работу над одной крупной задачей в одной активной ветке.

Правила:

- в одном агентском рабочем дереве одновременно не ведутся две независимые активные ветки;
- перед началом новой задачи дерево должно быть в чистом состоянии;
- в дереве не должно оставаться незакоммиченных изменений, незавершённого merge, rebase или cherry-pick;
- после завершения одного цикла работы агентское рабочее дерево может быть использовано для новой ветки.

## Готовность ветки к merge в develop

Рабочая ветка считается готовой к merge в `develop` только если:

- в неё влит актуальный `develop`;
- все конфликты после вливания `develop` явно разрешены;
- после синхронизации с `develop` повторно выполнены необходимые проверки и тесты;
- ветка остаётся в проверяемом состоянии.

Только после этого рабочая ветка передаётся на review и merge в `develop`.

## Merge рабочей ветки в develop

Merge рабочей ветки в `develop` выполняется только по явному запросу на финализацию изменений.

Merge выполняется из основного интеграционного рабочего дерева под контролем человека.

После merge необходимо:

1. Прогнать все тесты проекта.
2. Убедиться, что интеграция не сломала существующее поведение.

Если после merge тесты не проходят:

1. Исправления вносятся в ту же рабочую ветку.
2. После исправлений изменения повторно мержатся в `develop`.
3. Тесты запускаются заново до получения полностью зелёного результата.

После успешного merge и прохождения всех тестов рабочая ветка может быть удалена.

## Релизный процесс

Релиз инициируется только по прямому запросу пользователя.

Для первого релиза нужен короткий практический путь, а не общий процесс ради процесса.

Порядок релиза:

1. Завершить нужные рабочие ветки и влить их в `develop`.
2. На `develop` проверить, что пользовательские обещания в `README.md` и `docs/user-functions.md` соответствуют фактическому состоянию продукта.
3. На `develop` зафиксировать актуальный список команд для BotFather, если он менялся.
4. На `develop` прогнать полный набор тестов `pytest`.
5. Если релиз включает изменения схемы БД, отдельно проверить миграции и отметить это в итоговом описании релиза.
6. Только после этого по прямому запросу пользователя провести `develop` в `main` через pull request с учётом защиты ветки `main`.
7. После merge выполнить короткую smoke-проверку релизной версии.

### Теги релиза

Для первого релиза используется самое простое versioning по major-версиям:

- `v1`
- `v2`
- `v3`

Правила:

- релизный тег ставится на готовый commit в `main`;
- тег означает, что именно эта ревизия должна быть развернута на сервере;
- для первого релиза не используются `v1.1.0`, `v1.0.1` и другие более детальные схемы.

### Автодеплой по тегу

Если в GitHub push'ится новый релизный тег вида `v1`, `v2`, `v3`, срабатывает workflow:

`/.github/workflows/release-on-tag.yml`

Этот workflow также можно запустить вручную через `workflow_dispatch` и передать `git_ref`, например `main`, чтобы безопасно проверить деплой до первого релизного тега.

Что делает workflow:

1. Подключается к серверу по SSH.
2. Переходит в каталог проекта.
3. Делает `git fetch --tags origin`.
4. Делает `git checkout <tag>`.
5. Запускает `./scripts/release.sh`.

Для этого в GitHub repository secrets должны быть заданы:

- `DEPLOY_HOST`
- `DEPLOY_USER`
- `DEPLOY_SSH_KEY`
- `DEPLOY_PROJECT_DIR`

На текущем шаге workflow использует стандартный SSH-порт `22`.

Что обязательно проверить перед первым релизом:

- команды Telegram и их описания соответствуют фактическому UX;
- в документации нет обещаний про ещё неготовые сценарии;
- сценарий редактирования записей не фигурирует как доступная функция релиза.

## Проверки

Базовое ожидание по тестам:

- для тестов используется `pytest`;
- для тестирования Telegram-бота следует предпочитать решения, совместимые с `aiogram`;
- после синхронизации рабочей ветки с `develop` должен выполняться повторный прогон нужных проверок;
- после интеграции рабочей ветки в `develop` должен выполняться полный прогон тестов.

## Команды Telegram

Список команд для BotFather должен храниться в репозитории и обновляться в том же рабочем цикле, когда меняются пользовательские команды или их смысл.

Для первого релиза используется такой набор.

Пользовательские команды:

```text
start - начать работу с ботом
health - проверить доступность бота
today - показать итог за текущий день
report - показать отчёт за период
recent - показать последние записи
goal - посмотреть или изменить цели
settings - настроить отображение summary
provider - настроить LLM-провайдера
files - управлять файлами импорта и экспорта
```

Админ-команды:

```text
admin - показать состояние системы
```

Этот список должен быть пригоден для прямой передачи в BotFather без дополнительных догадок.

## Обязанности агента

При работе с задачами агент должен:

- учитывать этот workflow как обязательный;
- не предлагать работу напрямую в `main` или `develop`, кроме случаев, когда это явно соответствует согласованному процессу;
- работать внутри выделенного агентского рабочего дерева и не считать его финальной точкой принятия решения об интеграции в `develop`;
- напоминать о зависимостях, если запрошенная доработка требует отсутствующего базового слоя;
- напоминать о необходимости ADR при изменениях модели данных, схемы БД и ключевых архитектурных решений;
- в конце работы явно сообщать, что было проверено, а что не было проверено.
