# Development Workflow

## Назначение

Этот документ фиксирует рабочий процесс разработки, правила работы с ветками и порядок подготовки релиза в проекте `food_registry_bot`.

## Ветки

В проекте используются две долго живущие ветки:

- `main`
- `develop`

### Роли веток

- `main` содержит состояние, соответствующее готовому релизу.
- `develop` является основной веткой интеграции текущей разработки.

## Feature-ветки

Всю разработку следует вести в отдельных feature-ветках.

Правила:

- feature-ветки создаются от `develop`;
- одна feature-ветка соответствует одной логической задаче или доработке;
- для именования feature-веток следует использовать префикс `codex/`, если не согласовано иное;
- прямую разработку в `main` и `develop` следует избегать.

Пример имени ветки:

`codex/add-entry-model`

## Жизненный цикл задачи

1. Убедиться, что задача не зависит от ещё не реализованной базовой функциональности.
2. Если зависимость есть, явно обозначить её и не начинать реализацию, пока не согласован или не выполнен необходимый базовый этап.
3. Создать feature-ветку от `develop`.
4. Выполнить изменение короткими инкрементами, сохраняя проект в проверяемом состоянии.
5. Если изменение затрагивает доменную модель, схему БД или архитектурное решение, проверить необходимость нового ADR.
6. Обновить документацию, если изменились сценарии, ограничения или инженерные договорённости.
7. По запросу на финализацию изменений выполнить merge feature-ветки обратно в `develop`.

## Merge feature-ветки в develop

Merge feature-ветки в `develop` выполняется только по явному запросу на финализацию изменений.

После merge необходимо:

1. Прогнать все тесты проекта.
2. Убедиться, что интеграция не сломала существующее поведение.

Если после merge тесты не проходят:

1. Исправления вносятся в ту же feature-ветку.
2. После исправлений изменения повторно мержатся в `develop`.
3. Тесты запускаются заново до получения полностью зелёного результата.

После успешного merge и прохождения всех тестов feature-ветка может быть удалена.

## Релизный процесс

Релиз инициируется только по прямому запросу пользователя.

Для первого релиза нужен короткий практический путь, а не общий процесс ради процесса.

Порядок релиза:

1. Завершить нужные feature-ветки и влить их в `develop`.
2. На `develop` проверить, что пользовательские обещания в `README.md` и `docs/user-functions.md` соответствуют фактическому состоянию продукта.
3. На `develop` зафиксировать актуальный список команд для BotFather, если он менялся.
4. На `develop` прогнать полный набор тестов `pytest`.
5. Если релиз включает изменения схемы БД, отдельно проверить миграции и отметить это в итоговом описании релиза.
6. Только после этого по прямому запросу пользователя выполнить merge `develop` в `main`.
7. После merge выполнить короткую smoke-проверку релизной версии.

### Теги релиза

Для первого релиза используется самое простое versioning по major-версиям:

- `v1`
- `v2`
- `v3`

Правила:

- релизный тег ставится на готовый commit в `main`;
- тег означает, что именно эта ревизия должна быть развернута на сервере;
- для первого релиза не используются `v1.1.0`, `v1.0.1` и другие более детальные схемы.

### Автодеплой по тегу

Если в GitHub push'ится новый релизный тег вида `v1`, `v2`, `v3`, срабатывает workflow:

`/.github/workflows/release-on-tag.yml`

Этот workflow также можно запустить вручную через `workflow_dispatch` и передать `git_ref`, например `main`, чтобы безопасно проверить деплой до первого релизного тега.

Что делает workflow:

1. Подключается к серверу по SSH.
2. Переходит в каталог проекта.
3. Делает `git fetch --tags origin`.
4. Делает `git checkout <tag>`.
5. Запускает `./scripts/release.sh`.

Для этого в GitHub repository secrets должны быть заданы:

- `DEPLOY_HOST`
- `DEPLOY_USER`
- `DEPLOY_SSH_KEY`
- `DEPLOY_PROJECT_DIR`

На текущем шаге workflow использует стандартный SSH-порт `22`.

Что обязательно проверить перед первым релизом:

- команды Telegram и их описания соответствуют фактическому UX;
- в документации нет обещаний про ещё неготовые сценарии;
- сценарий редактирования записей не фигурирует как доступная функция релиза.

## Проверки

Базовое ожидание по тестам:

- для тестов используется `pytest`;
- для тестирования Telegram-бота следует предпочитать решения, совместимые с `aiogram`;
- после интеграции feature-ветки в `develop` должен выполняться полный прогон тестов.

## Команды Telegram

Список команд для BotFather должен храниться в репозитории и обновляться в том же рабочем цикле, когда меняются пользовательские команды или их смысл.

Для первого релиза используется такой набор.

Пользовательские команды:

```text
start - начать работу с ботом
health - проверить доступность бота
today - показать итог за текущий день
recent - показать последние записи
goal - посмотреть или изменить цели
settings - настроить отображение summary
files - управлять файлами импорта и экспорта
```

Админ-команды:

```text
admin - показать состояние системы
admin_users - показать известных пользователей
admin_allow - разрешить доступ пользователю
admin_deny - запретить доступ пользователю
admin_delete_entries - удалить все записи пользователя по Telegram ID
admin_backfill_nutrition - дозаполнить неполные nutrition metrics
```

Этот список должен быть пригоден для прямой передачи в BotFather без дополнительных догадок.

## Обязанности агента

При работе с задачами агент должен:

- учитывать этот workflow как обязательный;
- не предлагать работу напрямую в `main` или `develop`, кроме случаев, когда это явно соответствует согласованному процессу;
- напоминать о зависимостях, если запрошенная доработка требует отсутствующего базового слоя;
- напоминать о необходимости ADR при изменениях модели данных, схемы БД и ключевых архитектурных решений;
- в конце работы явно сообщать, что было проверено, а что не было проверено.
