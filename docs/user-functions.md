# Пользовательские функции бота

Этот документ фиксирует пользовательские функции бота в формате:

- что делает пользователь;
- что сохраняется в системе;
- какой результат получает пользователь.

Документ описывает именно пользовательский контракт. Если реализация меняется, но наблюдаемое поведение для пользователя остаётся тем же, документ обновлять не нужно. Если меняется доступный сценарий, входной формат или результат, документ нужно обновить в том же рабочем цикле.

Для первого релиза в этом документе действует правило:

- если сценарий доступен пользователю сейчас, он описывается в разделе `Доступно сейчас`;
- если сценарий только планируется, он выносится в `WIP` или в список того, что не входит в текущий релиз;
- сценарий редактирования записей в пользовательские обещания текущего релиза не входит.

## Доступно сейчас

### Доступ к боту по разрешению

Что делает пользователь:

- отправляет команду или сообщение боту.

Что делает система:

- проверяет, является ли пользователь админом из конфигурации;
- если нет, проверяет, разрешён ли пользователю доступ;
- если это новый пользователь без разрешения, создаёт для него запись ожидания admin-решения со статусом denied;
- если доступ не разрешён, не выполняет команды и не создаёт записи в БД.

Что получает пользователь:

- если доступ не разрешён, сообщение `Доступ к боту не разрешён.`

### Админ-разрешение пользователя

Что делает админ:

- отправляет `/admin_allow <telegram_user_id>`.

Что делает система:

- сохраняет или обновляет запись доступа пользователя;
- помечает пользователя как разрешённого.

Что получает админ:

- сообщение вида `Доступ разрешён для пользователя 123456789.`

### Админ-запрет пользователя

Что делает админ:

- отправляет `/admin_deny <telegram_user_id>`.

Что делает система:

- сохраняет или обновляет запись доступа пользователя;
- помечает пользователя как запрещённого.

Что получает админ:

- сообщение вида `Доступ запрещён для пользователя 123456789.`

### Админ-список пользователей

Что делает админ:

- отправляет `/admin_users`.

Что делает система:

- собирает известных пользователей из профилей `users` и записей доступа `user_access`;
- помечает админов из конфига отдельно от обычных пользователей;
- для обычных пользователей показывает текущий статус доступа и готовую следующую команду.

Что получает админ:

- сообщение вида:

```text
Пользователи:
- 123456789 @alice [allowed]
/admin_deny 123456789
- 987654321 @bob [denied]
/admin_allow 987654321
- 468995539 [admin]
```

### Админ-обзор системы

Что делает админ:

- отправляет `/admin`.

Что делает система:

- показывает текущую версию бота;
- показывает текущего админа;
- показывает число админов в конфиге;
- показывает число известных, разрешённых и запрещённых пользователей;
- показывает число `food entries` без полного набора nutrition metrics;
- показывает текущий статус `backfill nutrition`: `idle`, `running`, `completed` или `failed`;
- показывает список доступных admin-команд.

Что получает админ:

- сообщение вида:

```text
Панель администратора:
- версия бота: v1
- текущий админ: 468995539
- админов в конфиге: 1
- известных пользователей: 3
- разрешённых пользователей: 1
- запрещённых пользователей: 2
- пользователей с профилем: 1
- food entries без полного набора метрик: 16
- дозаполнение nutrition metrics: idle

Доступные команды:
- /admin
- /admin_users
- /admin_allow TELEGRAM_USER_ID
- /admin_deny TELEGRAM_USER_ID
- /admin_delete_entries TELEGRAM_USER_ID
- /admin_backfill_nutrition [LIMIT]
```

### Удаление всех записей пользователя администратором

Что делает админ:

- отправляет `/admin_delete_entries TELEGRAM_USER_ID`.

Что делает система:

- проверяет, что команду вызвал админ;
- находит профиль пользователя по `telegram_user_id`;
- считает, сколько `entries` будет удалено;
- не удаляет их сразу, а показывает сообщение подтверждения;
- удаляет записи только после отдельного явного подтверждения кнопкой.

Что получает админ:

- сначала сообщение-подтверждение с `telegram_user_id` пользователя и количеством записей для удаления;
- после подтверждения сообщение вида `Удалено записей пользователя TELEGRAM_USER_ID: N.`;
- при отмене сообщение, что удаление отменено;
- если аргумент не передан, сообщение `Использование: /admin_delete_entries TELEGRAM_USER_ID`;
- если пользователь с таким `telegram_user_id` не найден, сообщение об этом.

### Уведомление админов о запуске бота

Что делает система:

- при каждом запуске бота отправляет сообщение всем `ADMIN_USER_IDS`;
- в сообщении указывает, что бот запущен, и передаёт версию сборки;
- в качестве версии использует:
  - значение `APP_VERSION`, если оно передано окружением сборки;
  - точный git tag, если текущий коммит помечен тегом;
  - имя текущей ветки, если запуск идёт из рабочей копии;
  - package version или иное fallback-значение, если git недоступен.

Что получает админ:

- служебное сообщение вида:

```text
Бот запущен.
Версия: feature/import-export
```

### Админ-backfill nutrition

Что делает админ:

- отправляет `/admin_backfill_nutrition`;
- при необходимости отправляет `/admin_backfill_nutrition 50`, чтобы изменить лимит за один запуск.

Что делает система:

- находит `food entries`, у которых не хватает одной или нескольких метрик `calories`, `protein`, `fat`, `carbs`, `fiber`;
- берёт до `LIMIT` записей, по умолчанию `20`;
- запускает backfill в фоне и не блокирует обработку других admin-команд;
- повторно запускает nutrition estimation только для этих записей;
- сохраняет или обновляет метрики на уровне `entry_item`.

Пока backfill выполняется, `/admin` показывает статус вида:

```text
- backfill nutrition: running (selected 14, processed 4, remaining 10, skipped 0, failed 0, limit 20)
```

Что получает админ:

- сначала сообщение о старте:

```text
Запускаю backfill nutrition. Лимит: 20.
```

- затем отдельное сообщение по завершении, например:

```text
Backfill nutrition завершён.
Выбрано entries: 3
Обработано entries: 3
Сохранено метрик: 15
```

### Регистрация при первом сообщении

Что делает пользователь:

- отправляет `/start`;
- или просто пишет боту первое сообщение.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- создаёт пользователя в таблице `users`, если его ещё нет;
- привязывает пользователя к `telegram_user_id`;
- сохраняет `username`, если он есть;
- использует часовой пояс `Europe/Moscow` по умолчанию.

Что получает пользователь:

- текстовое подтверждение, что профиль создан или уже существует;
- reply keyboard с доступной кнопкой воды.

### Проверка доступности бота

Что делает пользователь:

- отправляет `/health`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- не пишет данные в БД;
- возвращает простой технический ответ.

Что получает пользователь:

- сообщение `ok`.

### Загрузка CSV-файла для будущего импорта

Что делает пользователь:

- отправляет в бот `csv`-файл как `document`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- пытается распознать файл как поддержанный обменный `csv` с данными еды, воды или тренировок по заголовкам файла, а не по имени файла;
- допускает как полный файл, так и неполный файл с минимальным обязательным набором полей;
- если файл не подходит, не сохраняет новый файловый артефакт;
- если файл является точным дублем уже загруженного импортного файла, не сохраняет новый файловый артефакт;
- если файл содержит строку, которая дублирует уже существующие данные пользователя, не сохраняет новый файловый артефакт и указывает первую проблемную строку;
- если лимит импортных файлов уже достигнут, не сохраняет новый файловый артефакт;
- если файл подходит, сохраняет локальную копию и создаёт запись подготовленного импортного файла со статусом `готов`.

Что получает пользователь:

- при успешной проверке полного файла сообщение, что файл принят и подготовлен к импорту, с краткой сводкой:
  - распознан тип файла `еда и вода`;
  - сколько будет создано записей еды;
  - сколько будет создано записей воды;
  - диапазон дат;
  - статус `готов`;
- при успешной проверке неполного файла сообщение, что файл принят и подготовлен к импорту:
  - распознан тип файла `еда и вода (неполный файл)`;
  - после импорта часть итогов может быть неполной;
- при успешной проверке workout-файла сообщение, что файл принят и подготовлен к импорту:
  - распознан тип файла `тренировки`;
  - число тренировок;
  - диапазон дат;
- при неподдержанном формате сообщение, что бот не знает, как обработать этот `csv`;
- при точном дубле сообщение `Такой файл уже был загружен ранее.`;
- при дубле данных сообщение с первой проблемной строкой;
- при превышении лимита сообщение с просьбой удалить лишний файл через `/files`.

Формат данных, который поддерживается сейчас:

- файл должен быть `csv`;
- файл должен содержать строку заголовков;
- для полного пользовательского импорта файл использует следующий набор колонок:
  - `Дата`
  - `Приём пищи`
  - `Блюдо / продукт`
  - `Категории`
  - `Количество`
  - `Единица`
  - `Ккал`
  - `Белки, г`
  - `Жиры, г`
  - `Углеводы, г`
  - `Клетчатка, г`
  - `Комментарий`
  - `Источник оценки`
  - `Уверенность оценки`
- для ослабленного варианта обязательны только:
  - `Дата`
  - `Блюдо / продукт`
  - `Количество`
  - `Единица`
- в ослабленном варианте остальные колонки из полного контракта остаются опциональными;
- для еды поле `Единица` не ограничено жёстким справочником:
  - бот принимает стандартные и нестандартные текстовые значения вроде `г`, `мл`, `банка`, `порция`, `порции`;
  - поле `Количество` при этом должно содержать число;
- если в food-строке уже заполнены метрики `Ккал`, `Белки, г`, `Жиры, г`, `Углеводы, г`, `Клетчатка, г`, нестандартная единица сама по себе не мешает импорту;
- если файл неполный и метрики планируется дозаполнять позже, нестандартные единицы вроде `банка` или `порция` могут ухудшать качество последующего дозаполнения по сравнению с `г` и `мл`;
- для workout-импорта поддерживается отдельный `csv` с колонками:
  - `Дата`
  - `Тип`
  - `Длительность, мин`
  - `Ккал тренировки`
- в workout-файле опционально поддерживаются:
  - `Интенсивность`
  - `Ккал учитывать в питании`
  - `Учитывать`
  - `Комментарий`
- workout-импорт создаёт `workout entries` с продолжительностью в `min`, `workout_calories` и `workout_calorie_credit`;
- для воды применяется отдельная нормализация:
  - если строка распознана как вода, единица сохраняется как `ml`, а позиция сохраняется как `water`;
- экспорт еды и воды создаётся в полном food/water-контракте;
- если у пользователя есть тренировки, бот дополнительно подготавливает отдельный workout-`csv` в workout-контракте.

### Список файлов импорта и экспорта

Что делает пользователь:

- отправляет `/files`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- показывает общий список импортных и экспортных файлов пользователя;
- сортирует список так, чтобы необработанные файлы были выше обработанных;
- в пределах группы показывает сначала импортные файлы, затем экспортные;
- для каждого файла показывает его `id`, чтобы на него можно было сослаться при обращении к администратору;
- для каждого файла показывает короткий статус `готов`, `обработан` или `ошибка`;
- для импортного файла показывает распознанный тип файла;
- для неполного импортного файла дополнительно показывает, что после импорта часть итогов может быть неполной;
- для workout-файла показывает число тренировок;
- даёт кнопки действий:
  - создать экспорт;
  - импортировать подходящий импортный файл;
  - скачать экспортный файл;
  - удалить файл;
  - обновить список.

Что получает пользователь:

- сообщение со списком файлов или сообщение, что файлов пока нет;
- inline-кнопки для действий над файлами.

### Явный запуск импорта из подготовленного файла

Что делает пользователь:

- открывает `/files`;
- выбирает импортный файл со статусом `готов` или `ошибка`;
- нажимает кнопку импорта.

Что делает система:

- читает локальную копию ранее сохранённого файла;
- повторно проверяет, не появились ли дублирующие данные;
- если импорт проходит успешно, создаёт записи еды и воды в БД и помечает файл как `обработан`;
- если во время запуска импорта обнаруживается конфликт по данным, помечает файл как `ошибка`.

Что получает пользователь:

- при успешном food/water-импорте сообщение с числом созданных записей еды и воды и указанием, что файл помечен как обработанный;
- при успешном workout-импорте сообщение с числом созданных тренировок и указанием, что файл помечен как обработанный;
- при неуспешном импорте сообщение с причиной ошибки;
- для неполного файла пользователь после импорта может увидеть неполные дневные итоги и при необходимости попросить администратора запустить уже существующий `/admin_backfill_nutrition`;
- если файл уже был импортирован ранее, сообщение, что повторный импорт запрещён.

### Создание и получение экспорта

Что делает пользователь:

- открывает `/files`;
- нажимает кнопку создания экспорта;
- затем скачивает один или несколько подготовленных экспортных файлов из того же списка.

Что делает система:

- собирает текущие данные еды и воды пользователя в поддержанный обменный `csv`;
- если у пользователя есть тренировки, дополнительно собирает их в отдельный workout-`csv`;
- сохраняет локальные копии подготовленных экспортных файлов;
- создаёт одну или несколько записей экспортных файлов со статусом `готов`;
- при скачивании отправляет файл в Telegram и помечает его как `обработан`;
- если лимит экспортных файлов уже достигнут, не создаёт новый экспортный файл.

Что получает пользователь:

- после создания экспорта сообщение или callback-ответ, что файл или файлы готовы к скачиванию;
- после скачивания соответствующий `csv`-файл в Telegram;
- при превышении лимита сообщение с просьбой сначала удалить лишний экспортный файл через `/files`.

### Дозаполнение метрик после импорта неполного файла

Что делает пользователь:

- загружает неполный `csv`;
- сам запускает его импорт через `/files`;
- если после этого видит неполные итоги дня, просит администратора запустить дозаполнение nutrition metrics.

Что делает администратор:

- использует уже существующую команду `/admin_backfill_nutrition`.

Что делает система:

- после импорта неполного файла может обнаружить `food entries` без полного набора nutrition metrics;
- existing backfill выбирает такие записи и дозаполняет им недостающие значения;
- записи с уже полным набором метрик не требуют отдельной обработки.

Что получает администратор:

- тот же отчёт, который уже предусмотрен для `/admin_backfill_nutrition`.

### Просмотр последних записей

Что делает пользователь:

- отправляет `/recent` или `/recent COUNT`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- если указан `COUNT`, использует его как размер страницы, иначе берёт значение по умолчанию `5`;
- принимает для `COUNT` только целое число от `1` до `60`;
- находит последние записи текущего пользователя страницами;
- возвращает их в порядке от новых к старым;
- группирует выводимые записи по пищевым дням пользователя без агрегации метрик;
- показывает локальное время записи и сохранённые позиции записи в человекочитаемом виде;
- если записей больше размера страницы, добавляет inline-кнопки перехода между страницами;
- если записи есть, добавляет inline-кнопку `Выбрать для удаления`.

Что получает пользователь:

- если записи есть, сообщение вида:

```text
Последние записи (страница 1, по 5):

19.05.2026
1. 09:10 — вода (250 мл)
2. 08:30 — яблоко
```

- если записей пока нет, сообщение `Пока записей нет. Отправь еду текстом, фото блюда или нажми кнопку воды.`
- если `COUNT` некорректен, сообщение `Использование: /recent [COUNT], где COUNT от 1 до 60.`

### Удаление записи из recent

Что делает пользователь:

- отправляет `/recent`;
- нажимает `Выбрать для удаления`;
- при необходимости переходит между страницами кнопками `← Назад` и `Вперёд →`;
- выбирает одну из показанных последних записей кнопкой вида `09:10 · вода (250 мл)`;
- подтверждает удаление кнопкой `Подтвердить` или отменяет его кнопкой `Отмена`.

Что делает система:

- не удаляет запись сразу, а сначала показывает экран подтверждения;
- удаляет запись целиком как `entry`, а не отдельную позицию внутри записи;
- сохраняет текущую страницу recent при переходах, отмене и после удаления, а если страница опустела, показывает предыдущую доступную;
- после подтверждения обновляет текущее сообщение актуальным списком `/recent`;
- если кнопка устарела или запись уже удалена, не меняет данные и показывает безопасную ошибку.

Что получает пользователь:

- на этапе подтверждения сообщение вида:

```text
Удалить эту запись?

08:30 — яблоко, йогурт

Это действие необратимо. Если запись понадобится снова, её нужно будет создать заново.
```

- после успешного удаления обновлённый список recent без удалённой записи, например:

```text
Последние записи (страница 1, по 5):
1. 09:10 — вода (250 мл)
2. 07:45 — кофе
```

- если запись уже удалена или недоступна, сообщение `Запись уже удалена или недоступна.`

### Дневная nutrition summary за сегодня

Что делает пользователь:

- отправляет `/today`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- определяет локальную дату пользователя по его `timezone` и его настройке начала nutrition-day;
- выбирает `food entries` пользователя, у которых `occurred_at` попадает в текущий локальный nutrition-day `HH:00 -> HH:00`;
- суммирует сохранённые nutrition metrics по еде;
- отдельно выбирает `water entries` пользователя в тех же границах пищевого дня и суммирует воду в миллилитрах;
- если у пользователя включены тренировки, отдельно читает workout entries текущего nutrition-day;
- если у workout entries есть `workout_calorie_credit`, добавляет его только к calorie target дня, не меняя protein/fat/carbs/fiber goals;
- в пользовательском ответе показывает только те показатели, которые включены у пользователя в summary settings;
- выбирает формат вывода summary по пользовательской настройке режима отображения;
- строки с белками, жирами, углеводами, клетчаткой и водой начинаются с сокращений `Б:`, `Ж:`, `У:`, `Кл:`, `В:`;
- сам факт тренировки и её calories показываются отдельным workout block;
- если в текущем дне есть `food entries` без полного набора этих метрик, исключает их из итогов и помечает, что summary неполная.
- если в текущем дне есть `water entries` с неподдерживаемым форматом, исключает их из итогов воды и помечает, что итог воды неполный.

Что получает пользователь:

- если за текущий пищевой день нет ни записей еды, ни записей воды, сообщение `Сегодня пока нет сохранённых записей.`
- иначе сообщение вида:

```text
К: 540.0 / 1800 ккал
Б: 25.3 / 90 г
Ж: 18.1 / 60 г
У: 61.4 / 210 г
Кл: 14.8 / 25 г
В: 750.0 / 2000 мл
```

- если для текущего пищевого дня уже есть goal snapshot, включённые показатели показывают факт и цель:

```text
К: 540.0 / 1800 ккал
Б: 25.3 / 90 г
Ж: 18.1 / 60 г
У: 61.4 / 210 г
В: 750.0 / 2000 мл
```

- если для текущего пищевого дня уже есть goal snapshot и пользователь выбрал режим `бары`, включённые показатели показываются progress bar'ами, например:

```text
Ккал   [███░░░░░░░] 30.0% 540.0/1800 ккал
Б      [██░░░░░░░░] 28.1% 25.3/90 г
Ж      [███░░░░░░░] 30.2% 18.1/60 г
У      [██░░░░░░░░] 29.2% 61.4/210 г
Кл     [█████░░░░░] 59.2% 14.8/25 г
В      [███░░░░░░░] 37.5% 750.0/2000 мл
```

- если часть food entries за день исключена из-за неполных метрик, дополнительно сообщение содержит пометку вида:

```text
Есть записей еды без полного набора метрик: 1. Итог дня пока неполный.
```

- если часть water entries за день исключена из-за неподдерживаемого формата, дополнительно сообщение содержит пометку вида:

```text
Есть записей воды с неподдерживаемым форматом: 1. Итог воды пока неполный.
```

- если пользователь выключил показ калорий в summary settings, сообщение `В summary сейчас нет включённых показателей.`
- если в текущем дне есть тренировки, после nutrition summary показывается блок вида:

```text
Тренировки:
- 11:00 — бег (40 мин, 757.0 ккал)
```

### Опциональная запись тренировки текстом

Что делает пользователь:

- сначала при необходимости включает тренировки в `/settings`;
- затем отправляет явную запись вроде `тренировка: бег 40 минут` или `сегодня была силовая 50 минут`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- пропускает сообщение через routing;
- если запись тренировок выключена, не сохраняет сообщение и прозрачно предлагает включить функцию в `/settings`;
- если запись тренировок включена, извлекает `workout entry` из текста;
- сохраняет запись как `entry_type = workout`;
- сохраняет исходный текст сообщения в `source_text`;
- если у тренировки известны `workout_calories`, дополнительно сохраняет отдельную metric `workout_calorie_credit`;
- в первой реализации `workout_calorie_credit` считается по правилу: каждые полные `200 ккал` тренировки дают `100 ккал` зачёта в питание;
- calorie credit влияет только на дневную calorie goal / remaining calories и не меняет protein/fat/carbs/fiber goals.

Что получает пользователь:

- короткое подтверждение сохранения вида:

```text
Сохранил:
- бег (40 мин)
```

- если у тренировки есть calories, confirmation может сразу включать обновлённый day-report и workout block.

### Опциональная запись тренировки одним скриншотом

Что делает пользователь:

- сначала при необходимости включает тренировки в `/settings`;
- затем отправляет один скриншот из workout-приложения без необходимости расписывать тренировку текстом.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- пропускает изображение через journal routing;
- если запись тренировок выключена, не сохраняет скриншот и прозрачно предлагает включить функцию в `/settings`;
- если запись тренировок включена, пытается извлечь `workout entry` из содержимого скриншота;
- если пользователь прислал album или несколько изображений одной группой, не пытается разбирать их и просит прислать один основной скриншот;
- при достаточной уверенности сохраняет запись как `entry_type = workout`;
- если на скриншоте явно видны калории тренировки, сохраняет их как factual metric `workout_calories`;
- если сохранены `workout_calories`, дополнительно создаёт отдельную metric `workout_calorie_credit`;
- по умолчанию `workout_calorie_credit` считается по фиксированному правилу: каждые полные `200 ккал` тренировки дают `100 ккал` nutrition credit;
- не сохраняет состав упражнений, мышечные карты, зоны нагрузки и другие подробности screenshot breakdown на этом этапе.

Что получает пользователь:

- короткое подтверждение сохранения вида:

```text
Сохранил:
- тренировка (90 мин)
- калории тренировки: 757.0 ккал
- к компенсации питания: 300.0 ккал

К: 0.0 / 2557 ккал
...

Тренировки:
- 03:00 — тренировка (90 мин, 757.0 ккал, компенсация 300.0 ккал)
```

### Установка дневных nutrition goals

Что делает пользователь:

- отправляет `/goal 1800`;
- или отправляет `/goal protein 90`, `/goal fat 60`, `/goal carbs 210`, `/goal fiber 25`, `/goal water 2000`;
- или отправляет `/goal`, чтобы посмотреть текущее состояние.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- при переданном числе без кода метрики сохраняет текущую цель по калориям;
- при переданном `metric_code + value` сохраняет текущую цель по соответствующей метрике;
- определяет текущий пищевой день пользователя по его `timezone` и `nutrition_day_start_hour`;
- находит или создаёт `daily goal snapshot` для этого дня;
- если snapshot для дня уже существует, не пересчитывает его из нового текущего preference-state.

Что получает пользователь:

- сообщение вида:

```text

- белки: 90 г
- жиры: 60 г
- углеводы: 210 г
- клетчатка: 25 г
- вода: 2000 мл

Настройка:
- /goal 1800
- /goal protein 90
- /goal fat 60
- /goal carbs 210
- /goal fiber 25
- /goal water 2000

Пищевой день 2026-05-19:
- калории: 1800 ккал
- белки: 90 г
- жиры: 60 г
- углеводы: 210 г
- клетчатка: 25 г
- вода: 2000 мл
Часовой пояс дня: Europe/Moscow.
Начало пищевого дня: 04:00.
```

- блок `Настройка` в этом ответе показывает только команды для тех показателей, которые сейчас включены у пользователя в summary settings.

- если текущий пищевой день уже был зафиксирован раньше с другим значением, дополнительно сообщение, что snapshot текущего дня уже был зафиксирован и не изменился.

### Быстрая запись воды кнопкой

Что делает пользователь:

- нажимает кнопку `Вода 250 мл`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- создаёт `entry` типа `water`;
- создаёт один `entry_item`:
  - `name = water`
  - `quantity = 250`
  - `unit = ml`
- в `entries.source_text` сохраняет `250 мл`.

Что получает пользователь:

- сообщение вида:

```text
Сохранил:
- вода (250 мл)

К: 0.0 / 1800 ккал
Б: 0.0 / 90 г
Ж: 0.0 / 60 г
У: 0.0 / 210 г
Кл: 0.0 / 25 г
В: 250.0 / 2000 мл (+250.0 мл)
```

- после записи бот показывает тот же day-report, что и `/today`, но для затронутых показателей дополнительно выделяет вклад новой записи;
- если у пользователя включена настройка `Дельта записи`, в конце затронутых строк показывается суффикс вида `(+250.0 мл)`;
- если настройка `Дельта записи` выключена, суффикс скрывается;
- если у пользователя включён режим `бары`, для воды и других затронутых показателей используется шкала `█/▓/░`, где `▓` показывает объём, добавленный только что сохранённой записью.

### Текстовая или фото-запись еды с обязательными метриками

Что делает пользователь:

- отправляет текст с едой, например `гречка с курицей`;
- или отправляет фото еды, при необходимости с caption.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- сначала пропускает свободное сообщение через routing boundary между journal, conversation и ambiguous;
- передаёт в extraction layer только сообщения, которые классифицированы как journal;
- передаёт сообщение в extraction layer;
- ожидает нормализованный `entries` payload;
- создаёт отдельные `entry` и `entry_items` из extraction result;
- для всех `food` items после сохранения вызывает nutrition estimation;
- сохраняет метрики `calories`, `protein`, `fat`, `carbs`, `fiber` для каждого food item;
- сохраняет уровень доверия для каждой метрики;
- только после успешной записи и еды, и метрик возвращает ответ пользователю.
- если запись относится к еде и для неё доступен conversational LLM, может дополнительно построить короткий `nutrition coach` comment по новой записи и текущему состоянию дня;
- если такой comment был построен, он сохраняется в `entries.llm_comment` для food entries этого write flow;
- если post-entry comment generation не удалась, запись всё равно считается успешно сохранённой, а пользователь получает обычный confirmation response без отдельной ошибки.

Что получает пользователь:

- сообщение вида:

```text
Сохранил:
- гречка с курицей

К: 220.0 / 1800 ккал (+220.0 ккал)
Б: 7.6 / 90 г (+7.6 г)
Ж: 2.2 / 60 г (+2.2 г)
У: 42.8 / 210 г (+42.8 г)
Кл: 5.1 / 25 г (+5.1 г)
В: 0.0 / 2000 мл
```

- confirmation после записи использует тот же итог пищевого дня, что и `/today`;
- после successful food write flow confirmation может дополнительно содержать короткий комментарий с префиксом агента, например `Нутрициолог: ...`;
- этот комментарий строится по только что сохранённой записи, её delta и обновлённому factual state дня;
- комментарий остаётся коротким, не открывает длинный диалог и не создаёт conversational session;
- для коуч-агентов используется единый подход: комментарий показывается с русским display label агента, а не с внутренним техническим именем;
- если включена настройка `Дельта записи`, в `text` mode у затронутых строк добавляется суффикс `(+delta unit)`;
- если настройка выключена, этот суффикс скрывается;
- в `bars` mode у затронутых строк `█` показывает объём до записи, `▓` - вклад новой записи, `░` - оставшийся объём до цели;
- настройка `Дельта записи` управляет только суффиксом в конце строки и не отключает саму delta-подсветку `▓`.

Ограничения текущего шага:

- structured extraction для текста и фото может работать как через dev payload, так и через отдельно включённый LLM provider;
- длинный или неочевидный свободный текст может быть безопасно отклонён как ambiguous и не будет сохранён молча;
- если extraction provider не смог вернуть валидный structured payload, запись еды не создаётся;
- если nutrition provider вернул невалидный payload, запись еды тоже не создаётся;
- на текущем шаге просит LLM возвращать `item.name` на русском языке, даже если фото отправлено без caption;
- если на фото видно одно цельное блюдо, старается сохранить его одной позицией, а не раскладывать на ингредиенты по догадке;
- если масса неочевидна, nutrition estimate всё равно должна быть сохранена, но с более низким уровнем доверия;
- если у item единица измерения не поддерживается текущим nutrition contract, например `шт`, оценка всё равно строится по названию блюда без передачи `quantity/unit`;
- поддерживается один photo message за раз;
- используется только самое крупное фото из массива `message.photo`;
- если пользователь прислал photo album или media group, бот не пытается разбирать их и просит прислать одно основное фото;
- несколько фото в одном сообщении как отдельный продуктовый сценарий пока не поддерживаются;
- если extraction provider не умеет обрабатывать фото, сценарий не сработает.
- post-entry comment сейчас добавляется только после food write flow и может быть пропущен для multi-date записи.

### Свободный conversational запрос

Что делает пользователь:

- отправляет обычное текстовое сообщение с вопросом, просьбой о совете или обсуждением питания, воды, режима, целей или тренировок;
- например `Как добрать белок без лишних калорий?`

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- пропускает сообщение через routing boundary;
- если сообщение выглядит как conversational request, не отправляет его в extraction/save flow;
- не создаёт `entry`, `entry_items` и nutrition metrics;
- передаёт текст в `nutrition coach`;
- для ответа всегда собирает factual context текущего пищевого дня пользователя:
  - текущие итоги по калориям, белкам, жирам, углеводам, клетчатке и воде;
  - прогресс против дневных целей;
  - список factual workout entries текущего пищевого дня, если у пользователя включена workout-функция;
  - недавние сохранённые записи;
- `nutrition coach` получает workout context дня всегда, а не только по эвристике релевантности вопроса;
- `nutrition coach` может учитывать тренировку в расширенном nutrition-смысле, например для белка, углеводов, hydration и meal timing, но не должен выдавать выдуманные workout metrics;
- если у пользователя уже есть активная conversational coach session не старше одного часа, использует её краткий контекст и несколько последних conversational turns;
- если пользователь отвечает reply на предыдущее conversational сообщение `nutrition coach`, бот сначала пытается продолжить именно ту же coach session, даже если часовой TTL уже истёк;
- сохраняет только conversational turns `nutrition coach` в отдельную coach session memory, не смешивая их с journal entries;
- возвращает разговорный ответ отдельным сообщением.

Что получает пользователь:

- ответ `nutrition coach`, учитывающий текущее состояние дня;
- conversational reply приходит как reply на исходное сообщение.

Пример ответа:

```text
Чтобы добрать белок без лишних калорий, сегодня удобнее смотреть на нежирный творог, йогурт без сахара, куриную грудку, рыбу или яичные белки. Если хочешь, могу предложить 2-3 варианта ужина под остаток твоих калорий и белка.
```

Дополнительно на текущем шаге:

- `nutrition coach` умеет отвечать на meal-planning вопросы, вопросы о воде и общие health topics;
- если пользователь перечисляет доступные продукты текстом, бот может предложить, что лучше приготовить с учётом текущих метрик дня;
- `nutrition coach` хранит conversational memory в течение часа после последнего conversational message;
- короткие follow-up сообщения внутри активной coach session, например `это будет сценарий А`, продолжают разговор и не должны молча сохраняться как еда;
- reply на конкретный ответ `nutrition coach` имеет приоритет над обычным поиском активной сессии по TTL;
- если текст такого reply выглядит как явная запись факта, например `запиши кусок хлеба` или `съел яблоко`, сообщение всё равно идёт в factual logging, а не в coach reply;
- пользователь может отправить фото холодильника или доступных продуктов с явным coaching-caption вроде `что лучше приготовить из этого?`;
- такое сообщение идёт в `nutrition coach` вместе с самим изображением и не сохраняется как journal entry;
- фото без caption по-прежнему считается journal photo candidate, чтобы не размывать factual photo logging;
- граница остаётся консервативной: `conversation_photo` включается только при явном conversational cue в caption.

### Неоднозначное свободное сообщение

Что делает пользователь:

- отправляет свободный текст, по которому недостаточно надёжно понять, это запись факта или разговор;
- например длинное сообщение без явного вопроса и без явных признаков записи.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- пропускает сообщение через routing boundary;
- если классификация недостаточно надёжна, не создаёт запись в БД;
- не отправляет сообщение ни в journal extraction flow, ни в conversational assistant как уже выбранный маршрут;
- возвращает короткий прозрачный ответ с просьбой уточнить намерение.

Что получает пользователь:

- сообщение вида:

```text
Не понял, это запись в дневник или вопрос.
Если хочешь сохранить факт, пришли явную запись еды или воды.
Если хочешь совет или объяснение, задай вопрос прямо.
```
