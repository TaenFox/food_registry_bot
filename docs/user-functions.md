# Пользовательские функции бота

Этот документ фиксирует пользовательские функции бота в формате:

- что делает пользователь;
- что сохраняется в системе;
- какой результат получает пользователь.

Документ описывает именно пользовательский контракт. Если реализация меняется, но наблюдаемое поведение для пользователя остаётся тем же, документ обновлять не нужно. Если меняется доступный сценарий, входной формат или результат, документ нужно обновить в том же рабочем цикле.

## Доступно сейчас

### Доступ к боту по разрешению

Что делает пользователь:

- отправляет команду или сообщение боту.

Что делает система:

- проверяет, является ли пользователь админом из конфигурации;
- если нет, проверяет, разрешён ли пользователю доступ;
- если это новый пользователь без разрешения, создаёт для него запись ожидания admin-решения со статусом denied;
- если доступ не разрешён, не выполняет команды и не создаёт записи в БД.

Что получает пользователь:

- если доступ не разрешён, сообщение `Доступ к боту не разрешён.`

### Админ-разрешение пользователя

Что делает админ:

- отправляет `/admin_allow <telegram_user_id>`.

Что делает система:

- сохраняет или обновляет запись доступа пользователя;
- помечает пользователя как разрешённого.

Что получает админ:

- сообщение вида `Доступ разрешён для пользователя 123456789.`

### Админ-запрет пользователя

Что делает админ:

- отправляет `/admin_deny <telegram_user_id>`.

Что делает система:

- сохраняет или обновляет запись доступа пользователя;
- помечает пользователя как запрещённого.

Что получает админ:

- сообщение вида `Доступ запрещён для пользователя 123456789.`

### Админ-список пользователей

Что делает админ:

- отправляет `/admin_users`.

Что делает система:

- собирает известных пользователей из профилей `users` и записей доступа `user_access`;
- помечает админов из конфига отдельно от обычных пользователей;
- для обычных пользователей показывает текущий статус доступа и готовую следующую команду.

Что получает админ:

- сообщение вида:

```text
Пользователи:
- 123456789 @alice [allowed]
/admin_deny 123456789
- 987654321 @bob [denied]
/admin_allow 987654321
- 468995539 [admin]
```

### Админ-обзор системы

Что делает админ:

- отправляет `/admin`.

Что делает система:

- показывает текущего админа;
- показывает число админов в конфиге;
- показывает число известных, разрешённых и запрещённых пользователей;
- показывает число `food entries` без полного набора nutrition metrics;
- показывает текущий статус `backfill nutrition`: `idle`, `running`, `completed` или `failed`;
- показывает список доступных admin-команд.

Что получает админ:

- сообщение вида:

```text
Admin dashboard:
- текущий админ: 468995539
- админов в конфиге: 1
- известных пользователей: 3
- разрешённых пользователей: 1
- запрещённых пользователей: 2
- пользователей с профилем: 1
- food entries без полного набора метрик: 16
- backfill nutrition: idle

Доступные команды:
- /admin
- /admin_users
- /admin_allow TELEGRAM_USER_ID
- /admin_deny TELEGRAM_USER_ID
- /admin_backfill_nutrition [LIMIT]
```

### Админ-backfill nutrition

Что делает админ:

- отправляет `/admin_backfill_nutrition`;
- при необходимости отправляет `/admin_backfill_nutrition 50`, чтобы изменить лимит за один запуск.

Что делает система:

- находит `food entries`, у которых не хватает одной или нескольких метрик `calories`, `protein`, `fat`, `carbs`;
- берёт до `LIMIT` записей, по умолчанию `20`;
- запускает backfill в фоне и не блокирует обработку других admin-команд;
- повторно запускает nutrition estimation только для этих записей;
- сохраняет или обновляет метрики на уровне `entry_item`.

Пока backfill выполняется, `/admin` показывает статус вида:

```text
- backfill nutrition: running (selected 14, processed 4, remaining 10, skipped 0, failed 0, limit 20)
```

Что получает админ:

- сначала сообщение о старте:

```text
Запускаю backfill nutrition. Лимит: 20.
```

- затем отдельное сообщение по завершении, например:

```text
Backfill nutrition завершён.
Выбрано entries: 3
Обработано entries: 3
Сохранено метрик: 12
```

### Регистрация при первом сообщении

Что делает пользователь:

- отправляет `/start`;
- или просто пишет боту первое сообщение.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- создаёт пользователя в таблице `users`, если его ещё нет;
- привязывает пользователя к `telegram_user_id`;
- сохраняет `username`, если он есть;
- использует часовой пояс `Europe/Moscow` по умолчанию.

Что получает пользователь:

- текстовое подтверждение, что профиль создан или уже существует;
- reply keyboard с доступной кнопкой воды.

### Проверка доступности бота

Что делает пользователь:

- отправляет `/health`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- не пишет данные в БД;
- возвращает простой технический ответ.

Что получает пользователь:

- сообщение `ok`.

### Просмотр последних записей

Что делает пользователь:

- отправляет `/recent`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- находит до пяти последних записей текущего пользователя;
- возвращает их в порядке от новых к старым;
- показывает сохранённые позиции записи в человекочитаемом виде.

Что получает пользователь:

- если записи есть, сообщение вида:

```text
Последние записи:
- вода: 250 мл
- яблоко
```

- если записей пока нет, сообщение `Пока нет сохранённых записей.`

### Дневная nutrition summary за сегодня

Что делает пользователь:

- отправляет `/today`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- определяет локальную дату пользователя по его `timezone` и его настройке начала nutrition-day;
- выбирает `food entries` пользователя, у которых `occurred_at` попадает в текущий локальный nutrition-day `HH:00 -> HH:00`;
- суммирует сохранённые nutrition metrics по еде;
- отдельно выбирает `water entries` пользователя в тех же границах пищевого дня и суммирует воду в миллилитрах;
- в пользовательском ответе показывает только те показатели, которые включены у пользователя в summary settings;
- выбирает формат вывода summary по пользовательской настройке режима отображения;
- строки с белками, жирами, углеводами и водой начинаются с сокращений `Б:`, `Ж:`, `У:`, `В:`;
- не учитывает другие non-food записи, кроме отдельного factual layer воды;
- если в текущем дне есть `food entries` без полного набора этих метрик, исключает их из итогов и помечает, что summary неполная.
- если в текущем дне есть `water entries` с неподдерживаемым форматом, исключает их из итогов воды и помечает, что итог воды неполный.

Что получает пользователь:

- если за текущий пищевой день нет ни записей еды, ни записей воды, сообщение `Сегодня пока нет сохранённых записей.`
- иначе сообщение вида:

```text
К: 540.0 / 1800 ккал
Б: 25.3 / 90 г
Ж: 18.1 / 60 г
У: 61.4 / 210 г
В: 750.0 / 2000 мл
```

- если для текущего пищевого дня уже есть goal snapshot, включённые показатели показывают факт и цель:

```text
К: 540.0 / 1800 ккал
Б: 25.3 / 90 г
Ж: 18.1 / 60 г
У: 61.4 / 210 г
В: 750.0 / 2000 мл
```

- если для текущего пищевого дня уже есть goal snapshot и пользователь выбрал режим `бары`, включённые показатели показываются progress bar'ами, например:

```text
К [███░░░░░░░] 30.0% 540.0/1800 ккал
Б [██░░░░░░░░] 28.1% 25.3/90 г
Ж [███░░░░░░░] 30.2% 18.1/60 г
У [██░░░░░░░░] 29.2% 61.4/210 г
В [███░░░░░░░] 37.5% 750.0/2000 мл
```

- если часть food entries за день исключена из-за неполных метрик, дополнительно сообщение содержит пометку вида:

```text
Есть записей еды без полного набора метрик: 1. Итог дня пока неполный.
```

- если часть water entries за день исключена из-за неподдерживаемого формата, дополнительно сообщение содержит пометку вида:

```text
Есть записей воды с неподдерживаемым форматом: 1. Итог воды пока неполный.
```

- если пользователь выключил показ калорий в summary settings, сообщение `В summary сейчас нет включённых показателей.`

### Настройки summary

Что делает пользователь:

- отправляет `/settings`;
- нажимает inline-кнопку переключения `Калории: on/off`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- находит или создаёт запись пользовательских summary settings;
- показывает текущие значения настроек `show_calories`, `show_protein`, `show_fat`, `show_carbs`, `show_water`;
- показывает текущее отображение summary;
- показывает текущее значение `начало дня`;
- при нажатии inline-кнопки меняет соответствующую настройку и обновляет это же сообщение.

Что получает пользователь:

- сообщение вида:

```text
Настройки summary:
- калории: включено
- белки: включено
- жиры: включено
- углеводы: включено
- вода: включено
- отображение: текст
- начало дня: 04:00
```

- inline-кнопки:
  - `Калории: on/off`
  - `Белки: on/off`
  - `Жиры: on/off`
  - `Углеводы: on/off`
  - `Вода: on/off`
  - `Отображение: текст/бары`
  - `Начало дня: HH:00`

### Установка дневных nutrition goals

Что делает пользователь:

- отправляет `/goal 1800`;
- или отправляет `/goal protein 90`, `/goal fat 60`, `/goal carbs 210`, `/goal water 2000`;
- или отправляет `/goal`, чтобы посмотреть текущее состояние.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- при переданном числе без кода метрики сохраняет текущую цель по калориям;
- при переданном `metric_code + value` сохраняет текущую цель по соответствующей метрике;
- определяет текущий пищевой день пользователя по его `timezone` и `nutrition_day_start_hour`;
- находит или создаёт `daily goal snapshot` для этого дня;
- если snapshot для дня уже существует, не пересчитывает его из нового текущего preference-state.

Что получает пользователь:

- сообщение вида:

```text
Текущие цели:
- калории: 1800 ккал
- белки: 90 г
- жиры: 60 г
- углеводы: 210 г
- вода: 2000 мл

Настройка:
- /goal 1800
- /goal protein 90
- /goal fat 60
- /goal carbs 210
- /goal water 2000

Пищевой день 2026-05-19:
- калории: 1800 ккал
- белки: 90 г
- жиры: 60 г
- углеводы: 210 г
- вода: 2000 мл
Часовой пояс дня: Europe/Moscow.
Начало пищевого дня: 04:00.
```

- блок `Настройка` в этом ответе показывает только команды для тех показателей, которые сейчас включены у пользователя в summary settings.

- если текущий пищевой день уже был зафиксирован раньше с другим значением, дополнительно сообщение, что snapshot текущего дня уже был зафиксирован и не изменился.

### Быстрая запись воды кнопкой

Что делает пользователь:

- нажимает кнопку `Вода 250 мл`.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- создаёт `entry` типа `water`;
- создаёт один `entry_item`:
  - `name = water`
  - `quantity = 250`
  - `unit = ml`
- в `entries.source_text` сохраняет `250 мл`.

Что получает пользователь:

- сообщение вида:

```text
Сохранил:
- вода: 250 мл
```

### Текстовая или фото-запись еды с обязательными метриками

Что делает пользователь:

- отправляет текст с едой, например `гречка с курицей`;
- или отправляет фото еды, при необходимости с caption.

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- передаёт сообщение в extraction layer;
- ожидает нормализованный `entries` payload;
- создаёт отдельные `entry` и `entry_items` из extraction result;
- для всех `food` items после сохранения вызывает nutrition estimation;
- сохраняет метрики `calories`, `protein`, `fat`, `carbs` для каждого food item;
- сохраняет уровень доверия для каждой метрики;
- только после успешной записи и еды, и метрик возвращает ответ пользователю.

Что получает пользователь:

- сообщение вида:

```text
Сохранил:
- гречка с курицей

КБЖУ по еде:
- калории: 220.0 ккал
- белки: 7.6 г
- жиры: 2.2 г
- углеводы: 42.8 г
```

Ограничения текущего шага:

- structured extraction для текста и фото может работать как через dev payload, так и через отдельно включённый LLM provider;
- если extraction provider не смог вернуть валидный structured payload, запись еды не создаётся;
- если nutrition provider вернул невалидный payload, запись еды тоже не создаётся;
- на текущем шаге просит LLM возвращать `item.name` на русском языке, даже если фото отправлено без caption;
- если на фото видно одно цельное блюдо, старается сохранить его одной позицией, а не раскладывать на ингредиенты по догадке;
- если масса неочевидна, nutrition estimate всё равно должна быть сохранена, но с более низким уровнем доверия;
- если у item единица измерения не поддерживается текущим nutrition contract, например `шт`, оценка всё равно строится по названию блюда без передачи `quantity/unit`;
- поддерживается один photo message за раз;
- используется только самое крупное фото из массива `message.photo`;
- несколько фото в одном сообщении как отдельный продуктовый сценарий пока не поддерживаются;
- если extraction provider не умеет обрабатывать фото, сценарий не сработает.

### Structured payload для extraction contract

Что делает пользователь:

- отправляет JSON с массивом `entries`, соответствующий extraction contract;
- в одном сообщении может передать сразу несколько записей, например еду и воду.

Поддерживаемый формат:

```json
{
  "entries": [
    {
      "type": "food",
      "occurred_at": "2026-05-18T10:15:00Z",
      "items": [
        {"name": "гречка", "quantity": 200, "unit": "г"},
        {"name": "курица", "quantity": 150, "unit": "г"}
      ]
    },
    {
      "type": "water",
      "items": [
        {"name": "вода", "quantity": 250, "unit": "мл"}
      ]
    }
  ]
}
```

Что делает система:

- сначала проверяет, разрешён ли пользователю доступ;
- валидирует JSON;
- валидирует extraction contract;
- для каждого элемента в `entries` создаёт отдельный `entry`;
- для каждого `entry` создаёт связанные `entry_items`;
- для всех `food` items после сохранения вызывает nutrition estimation;
- сохраняет метрики `calories`, `protein`, `fat`, `carbs` и confidence для каждой метрики;
- для воды и базовых единиц измерения нормализует входные варианты, например `вода`/`water`, `мл`/`ml`, `г`/`g`;
- для этого сценария не дублирует raw JSON в `entries.source_text`;
- если `occurred_at` не передан, подставляет текущее время;
- помечает созданные через этот сценарий `entry_items` как `source_type = extraction_payload`.

Что получает пользователь:

- список сохранённых позиций в формате `название: количество единица`;
- если в сообщении была еда, дополнительно получает КБЖУ по food items из этого сообщения.

Пример ответа:

```text
Сохранил:
- гречка: 200 г
- курица: 150 г
- вода: 250 мл

КБЖУ по еде:
- калории: 441.0 ккал
- белки: 16.2 г
- жиры: 5.4 г
- углеводы: 86.6 г
```

Если structured payload невалиден:

- запись в БД не создаётся;
- бот отвечает, что ожидает объект вида `{"entries": [...]}` с `type`, `items` и `name`.

## Ещё не реализовано

Ниже перечислены важные пользовательские функции, которые ожидаются по продуктовой модели, но пока не доступны:

- production LLM-разбор скриншотов тренировок и более сложных mixed-media сценариев;
- запись тренировок;
- сводка за день;
- редактирование и удаление сохранённых записей;
- работа с дневными целями.
