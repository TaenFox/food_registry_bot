# Проект: Импорт и экспорт данных через обменный файл в Telegram

Этот документ фиксирует согласованное направление развития импорта и экспорта пользовательских данных.

Цель документа:

- сохранить результат обсуждения в репозитории;
- зафиксировать пользовательский сценарий до реализации Telegram flow;
- отделить проектные решения по обменному файлу от деталей конкретной реализации;
- дать следующую понятную точку входа для новой сессии Codex.

Документ не заменяет ADR. Если очередной этап меняет доменную модель, пользовательский контракт, правила идемпотентности, схему БД или принципы хранения файлов, перед реализацией это нужно зафиксировать отдельным ADR.

## 1. Целевой результат

В проекте появляется файловый сценарий обмена данными через Telegram.

Система должна уметь:

- принять от пользователя `csv`-файл в чате;
- провалидировать, подходит ли файл под поддержанный контракт импорта;
- сохранить файл как подготовленный к обработке артефакт;
- показать пользователю список подготовленных файлов;
- запустить импорт только по явному выбору пользователя;
- отправить пользователю `csv`-файл с экспортом его данных;
- хранить информацию о подготовленных и выполненных импортных и экспортных файлах;
- позволять пользователю держать под контролем ограниченный набор файлов и удалять лишние.

На текущем этапе поддерживается только один контракт обменного файла.

На текущем этапе не вводятся:

- несколько форматов обменных файлов;
- инкрементальный экспорт;
- синхронизация с внешней системой;
- live-интеграция с Google Sheets;
- автоматический импорт сразу после загрузки файла.

## 2. Уже принято

Ниже перечислены решения, уже согласованные в обсуждении.

### 2.1. Импорт и экспорт идут через Telegram-файлы

Файловый обмен должен быть доступен пользователю внутри Telegram, а не только как локальная утилита разработчика.

Следствие:

- пользовательский контракт строится вокруг `document` в Telegram;
- локальный `csv`-importer рассматривается как внутренний технический слой, а не как конечный UX.

### 2.2. Импорт двухфазный

Загрузка файла и запись данных в БД не происходят в один шаг.

Ожидаемая модель:

- пользователь загружает `csv`;
- система валидирует его и сохраняет как подготовленный файл;
- пользователь отдельно выбирает подготовленный файл для запуска импорта;
- только после этого происходит фактическая запись данных.

### 2.3. На этом этапе поддерживается только один контракт обменного файла

На ближайшем этапе система должна понимать только один формат файла для импорта и один формат файла для экспорта.

Это значит:

- не нужно одновременно поддерживать `google sheet csv`, `bot export csv`, `xlsx` и другие варианты;
- формат должен быть строго определён;
- желательно сохранить возможность выгрузить файл и затем загрузить его обратно для проверки контракта;
- при этом допускается, что импортный и экспортный варианты будут немного различаться, если это потребуется реализации;
- любое расширение количества контрактов считается отдельным будущим усложнением.

Текущая реализованная спецификация:

- файл `csv`;
- полный набор колонок:
  - `Дата`
  - `Приём пищи`
  - `Блюдо / продукт`
  - `Категории`
  - `Количество`
  - `Единица`
  - `Ккал`
  - `Белки, г`
  - `Жиры, г`
  - `Углеводы, г`
  - `Клетчатка, г`
  - `Комментарий`
  - `Источник оценки`
  - `Уверенность оценки`
- первый контракт работает только для еды и воды.

Текущее уточнение контракта:

- для загрузки минимально допустимого файла обязательными должны стать только:
  - `Дата`
  - `Блюдо / продукт`
  - `Количество`
  - `Единица`
- остальные поля должны стать опциональными;
- неполный файл должен допускаться к обычному пользовательскому импорту;
- после такого импорта у части записей могут отсутствовать nutrition metrics;
- если пользователю нужно дозаполнить эти данные, администратор использует уже существующий backfill, без отдельного сценария обработки файла.

### 2.4. Инкрементальный экспорт сознательно не нужен

На текущем этапе экспорт всегда формируется как полная выгрузка выбранного набора данных, без механизма "экспортировать только новое".

Следствие:

- не нужно помечать записи как экспортированные;
- не нужен журнал экспортной синхронизации со slave-системой;
- не нужна модель экспортных курсоров или экспортных батчей ради дедупликации.

### 2.5. Пользователь управляет ограниченным набором файлов

Пользователь должен иметь список подготовленных файлов и возможность удалять лишние.

На текущем направлении принимается ограничение:

- у пользователя одновременно под управлением находится не более пяти импортных файлов;
- у пользователя одновременно под управлением находится не более пяти экспортных файлов.

Ограничение нужно для того, чтобы:

- не превращать бот в файловое хранилище;
- не перегружать UX списками;
- держать жизненный цикл файлов коротким и обозримым.

### 2.6. В первый контракт входят только еда и вода

На текущем этапе обменный файл работает только для записей еды и воды.

Следствие:

- тренировки не входят в первый импортный контракт;
- тренировки не входят в первый экспортный контракт;
- расширение файла до тренировок рассматривается как отдельный следующий шаг.

### 2.7. Повторный импорт нужно пытаться останавливать на этапе валидации

На текущем направлении система должна пытаться обнаруживать дубли до запуска фактического импорта.

Следствие:

- валидация должна проверять не только структуру файла, но и риск повторного импорта;
- пользователю нужно явно показывать, что файл выглядит как уже загруженный или уже импортированный;
- для обнаружения дублей нужно использовать оба критерия:
  - хэш всего файла;
  - проверку по содержимому строк.

### 2.8. Дубль не должен загружаться как новый файл

Если система на этапе валидации определила, что файл является дублем, такой файл не должен сохраняться как новый подготовленный артефакт.

Следствие:

- пользователь получает однозначную обратную связь, почему файл не принят;
- импорт по такому файлу не запускается;
- в списке файлов не появляется новая дублирующая запись.

### 2.9. Для файлов вводится признак обработки

У файлов должен быть наблюдаемый признак `обработан`.

На текущем направлении:

- для импортного файла `обработан` означает, что импорт по нему уже был выполнен;
- для экспортного файла `обработан` означает, что файл уже был отправлен пользователю в Telegram.

### 2.10. Повторный импорт обработанного файла запрещён

Если импортный файл уже был обработан, повторный импорт по нему не допускается.

Следствие:

- не нужен отдельный сценарий подтверждённого повторного запуска;
- обработанный импортный файл остаётся только наблюдаемым артефактом до удаления;
- сообщение пользователю должно явно объяснять, что файл уже был импортирован ранее.

### 2.11. Достаточно одной команды списка файлов

Пользовательский вход в управление файлами должен строиться вокруг одной общей команды списка файлов, а не отдельных команд для импорта и экспорта.

Следствие:

- экспорт создаётся через действие из `/files`, а не через отдельную обязательную команду `/export`;
- список файлов является основной точкой входа в оба сценария: импорт и экспорт.

### 2.12. Обработанные файлы остаются в списке до удаления

Обработанные файлы должны оставаться видимыми пользователю, пока он их не удалит.

При этом:

- в списке они показываются после необработанных файлов;
- для них достаточно короткого статуса без отдельной детальной карточки.

### 2.13. Работаем только с локальными копиями файлов

На текущем этапе файловые артефакты должны храниться как локальные копии внутри приложения.

Следствие:

- Telegram `file_id` не рассматривается как основной механизм хранения;
- повторная валидация и запуск импорта должны опираться на локально сохранённый файл;
- при удалении файла пользователем должна удаляться и соответствующая локальная копия.

### 2.14. При превышении лимита новый файл не добавляется

Если пользователь уже достиг лимита файлов в соответствующей категории, новый файл не должен сохраняться.

На текущем направлении:

- лимит импортных файлов проверяется отдельно от лимита экспортных файлов;
- лимит экспортных файлов проверяется отдельно от лимита импортных файлов;
- при достижении лимита пользователь получает явное сообщение, что сначала нужно удалить лишний файл.

## 3. Продуктовая рамка

### 3.1. Что считать первой полезной функциональностью

Первой полезной функциональностью считается не интеграция с внешней таблицей как таковая, а безопасный и понятный файловый обмен внутри Telegram.

Минимально полезный результат:

- пользователь может прислать `csv` в бот;
- бот умеет объяснить, подходит файл или нет;
- пользователь видит подготовленные файлы;
- пользователь сам решает, какой файл импортировать;
- пользователь может получить выгрузку своих данных в `csv`.

### 3.2. Что не входит в первый целостный шаг

В ближайший первый целостный шаг не входят:

- прямое чтение Google Sheets по ссылке;
- загрузка `xlsx`;
- пакетная обработка нескольких файлов одной командой;
- частичный повторный экспорт "только нового";
- двусторонняя синхронизация с внешней системой;
- автоматическое обновление ранее импортированных данных по повторной загрузке файла.

## 4. Основные пользовательские сценарии

### 4.1. Загрузка файла на проверку

Пользователь:

- отправляет в бот `csv`-файл.

Система:

- пытается распознать файл как допустимый импортный контракт;
- если файл не подходит, явно отвечает, что не знает, как его обработать;
- если файл подходит, сохраняет запись о файле как подготовленную к импорту;
- показывает предварительный результат проверки.

Предварительный результат проверки должен по возможности включать:

- подходит ли файл;
- сколько строк может быть импортировано;
- диапазон дат;
- какие типы данных будут созданы;
- есть ли ошибки или предупреждения.

### 4.2. Просмотр списка подготовленных файлов

Пользователь:

- вызывает отдельную команду списка файлов.

Система:

- показывает управляемый список подготовленных импортных и экспортных файлов пользователя;
- показывает статус файла;
- даёт действие для запуска импорта, скачивания экспорта или удаления файла.
- использует одну общую команду для входа в этот список.
- даёт действие для создания нового экспортного файла.

### 4.3. Явный запуск импорта

Пользователь:

- выбирает один из подготовленных файлов импорта.

Система:

- запускает импорт из уже провалидированного файла;
- по завершении помечает файл как выполненный или завершившийся ошибкой;
- присылает пользователю отчёт.

Отчёт должен различать как минимум:

- успешный импорт;
- частично успешный импорт;
- ошибку без записи данных.

### 4.4. Создание и получение экспорта

Пользователь:

- открывает `/files` и выбирает действие создания экспорта.

Система:

- формирует файл в единственном поддержанном контракте;
- сохраняет его как экспортный файловый артефакт;
- отправляет файл пользователю;
- помечает файл как обработанный после успешной отправки в Telegram;
- отражает файл в общем списке управляемых файлов.

Если лимит экспортных файлов уже достигнут, новый экспортный файл не создаётся.

## 5. Рекомендуемая техническая рамка

### 5.1. Нужна отдельная модель файловых артефактов

Файл в этом проекте является не временным байтовым объектом в handler, а отдельной сущностью с жизненным циклом.

Минимально ожидаемые свойства артефакта:

- пользователь-владелец;
- направление: импорт или экспорт;
- имя файла;
- telegram file id и/или локальный путь хранения;
- распознанный тип контракта;
- статус;
- краткий результат валидации;
- краткий результат выполнения;
- время загрузки / создания;
- время завершения обработки.

Минимально ожидаемые дополнительные признаки:

- обработан ли файл;
- к какому типу относится файл: импортный или экспортный;
- является ли файл дубликатом уже известного артефакта или уже импортированных данных.

### 5.2. Нужен строгий файловый контракт

Поскольку на этом этапе поддерживается только один контракт, он должен быть описан строго и проверяемо.

Важно избежать серой зоны, где система пытается "угадать", подходит ли произвольный `csv`.

Следствие:

- валидация должна быть консервативной;
- неподдержанный файл должен отклоняться явно;
- структура экспортируемого файла должна быть согласована заранее;
- желательно сохранить round-trip проверку: экспортированный файл должен быть по возможности пригоден для обратной загрузки.

### 5.3. Импорт не должен быть скрыто необратимым

Импорт меняет factual history, поэтому запуск должен быть отдельным осознанным действием.

Даже если предварительная валидация успешна, система не должна автоматически импортировать данные только потому, что файл был загружен.

### 5.4. Экспорт пока не должен вводить синхронизационную модель

Поскольку инкрементальный экспорт на этом этапе отклонён, экспортный слой должен оставаться простым:

- сформировать файл;
- сохранить артефакт экспорта;
- отдать файл пользователю.

Не нужно заранее добавлять:

- `exported_at` на записи;
- журнал "куда уже отправляли";
- идентификаторы slave-систем;
- курсоры инкрементальной синхронизации.

## 6. Открытые решения

Ниже перечислены решения, которые нужно принять до полноценной реализации.

### 6.1. Единый контракт обменного файла

Нужно определить:

- как именно будет оформлен ослабленный вариант минимального файла при сохранении одного контрактного семейства;
- включаются ли технические поля для более надёжного повторного импорта.

На текущий момент уже зафиксировано:

- полный рабочий набор колонок реализован;
- минимальный будущий набор для загрузки согласован концептуально, но не реализован.

### 6.2. Правила повторного импорта

Нужно определить:

- как именно формулируется пользовательская обратная связь при обнаружении дубля;
- нужно ли различать в сообщении "точный дубль файла" и "файл с уже импортированными данными".

### 6.3. Политика хранения файлов

Нужно определить:

- где именно хранится содержимое локальных копий файлов;
- что именно удаляется при удалении файла пользователем;
- удаляется ли файл автоматически после успешного импорта или экспорта.

### 6.4. Список управляемых файлов

Нужно определить:

- как сортируются файлы;
- нужны ли в списке отдельные короткие статусы для:
  - подготовлен;
  - обработан;
  - ошибка;
  - отклонён как дубль.

### 6.5. Пользовательские тексты при превышении лимита

Нужно определить:

- как формулируется сообщение при достижении лимита импортных файлов;
- как формулируется сообщение при достижении лимита экспортных файлов;
- нужно ли в этом сообщении сразу подсказывать команду `/files` и следующее действие удаления.
