# Проект: Действия с блюдами в `/recent`

Этот документ фиксирует предварительно согласованное направление развития команды `/recent`.

Цель документа:

- сохранить решения по UX до начала кодовых изменений;
- разделить первый полезный этап и дальнейшие усложнения;
- зафиксировать, где речь идёт о редактировании исторических данных, а где о создании новой записи;
- дать понятную точку входа для следующего инкремента реализации.

Документ не заменяет ADR. Если следующий этап потребует новой модели редактирования, отдельного состояния диалога, новых таблиц или изменения принципов хранения nutrition-данных, это нужно будет отдельно зафиксировать перед реализацией.

## 1. Целевой результат

Команда `/recent` должна перестать быть только списком записей с удалением целой записи.

На ближайшем этапе система должна уметь:

- показывать последние записи как и сейчас;
- позволять открыть конкретную запись еды и увидеть её блюда или продукты по отдельности;
- позволять удалить отдельное блюдо или продукт из записи, а не только всю запись целиком;
- позволять повторно записать отдельное блюдо или продукт как новый актуальный приём пищи;
- дать управляемый способ скорректировать порцию конкретного блюда внутри уже сохранённой записи;
- сохранять проект в проверяемом состоянии без новой сложной машины пользовательских состояний.

На ближайшем этапе в эту функциональность не входят:

- произвольное текстовое редактирование названия блюда;
- объединение нескольких старых блюд в одну новую запись;
- редактирование времени записи через `/recent`;
- отдельная история правок;
- массовые операции над несколькими блюдами одновременно.

## 2. Предлагаемое направление

Ниже перечислены решения, которые выглядят минимальными и практически полезными для первой итерации.

### 2.1. Первый экран `/recent` остаётся списком записей

Текущий список последних записей уже выполняет роль хорошей точки входа.

Следствие:

- команда `/recent` по-прежнему открывает список `Entry`;
- пагинация и группировка по пищевому дню сохраняются;
- вместо сценария только удаления у записи появляется отдельный сценарий действий.

### 2.2. На втором уровне открывается запись, а не сразу действие

После выбора записи пользователь должен сначала попасть в карточку конкретной записи, а уже внутри неё выбрать блюдо.

Рекомендуемый поток:

- список записей;
- открытие одной записи;
- список блюд или продуктов внутри записи;
- открытие действий для конкретного блюда.

Причина:

- у пользователя появляется наблюдаемая граница между записью и блюдом;
- не нужно перегружать первый экран длинными кнопками;
- на этом же экране можно сохранить действие удаления всей записи как запасной путь.

### 2.3. В первой версии item-level действия нужны прежде всего для food entries

Основной пользовательский запрос относится к блюдам внутри записи еды.

Следствие:

- `food`-записи получают второй уровень с блюдами;
- `water` и `workout` на первом этапе могут остаться на текущем entry-level сценарии;
- если внутри `/recent` выбрана запись воды или тренировки, достаточно сохранить существующее поведение без ложной глубины.

Это уменьшает объём первой итерации и не мешает позже расширить тот же паттерн.

### 2.4. Удаление блюда меняет только выбранную запись

Если пользователь удаляет одно блюдо из food entry, должна измениться только эта конкретная запись.

Согласованное поведение для первой версии:

- удаляется только выбранный `EntryItem`;
- остальные блюда внутри той же записи сохраняются;
- связанные `EntryItemMetric` удаляются каскадно вместе с блюдом;
- если удалён последний `EntryItem` записи, удаляется вся `Entry`.

Это поведение выглядит естественным и не требует отдельной модели "пустой записи".

### 2.5. Повтор блюда создаёт новую запись "сейчас", не переписывая прошлое

Сценарий "съел то же самое ещё раз" должен быть отдельным созданием новой записи, а не клонированием прошлого времени.

Согласованное поведение для первой версии:

- создаётся новая `food`-запись с одним выбранным блюдом;
- `occurred_at` ставится в текущее время;
- исходная запись не меняется;
- если у исходного блюда уже есть сохранённые nutrition metrics, они копируются в новую запись без повторного расчёта;
- если у исходного блюда nutrition metrics отсутствуют, новая запись тоже создаётся без них.

### 2.6. Изменение порции относится к исправлению прошлой записи

Сценарий изменения порции отличается от повтора.

Предлагаемое поведение:

- изменение порции редактирует выбранный `EntryItem` внутри уже существующей записи;
- это считается явным исправлением сохранённых данных пользователем;
- после изменения порции сохранённые nutrition metrics для выбранного блюда должны масштабироваться пропорционально коэффициенту изменения порции;
- на первом этапе для этого не нужен повторный расчёт через LLM.

Такое разделение делает два разных сценария явными:

- `Повторить сейчас` создаёт новое событие;
- `Изменить порцию` исправляет уже сохранённое событие.

### 2.7. Для первой версии редактирование порции лучше сделать без свободного текстового ввода

В текущем коде нет готовой пользовательской state machine для режима "ожидаю следующее сообщение как новую порцию".

Поэтому для первого инкремента предпочтительнее:

- не вводить отдельное ожидание следующего сообщения;
- использовать набор готовых кнопок изменения порции небольшим шагом;
- пересчитывать `quantity` и масштабировать nutrition metrics детерминированно.

Рекомендуемый первый набор действий:

- для `g`: `-10 г` и `+10 г`;
- для `ml`: `-10 мл` и `+10 мл`.

Следствие:

- сценарий получается быстрым и полностью inline;
- не появляется новый слой временного состояния пользователя;
- первую версию можно покрыть обычными handler-тестами.

### 2.8. Изменение порции доступно только там, где количество действительно наблюдаемо

Если у блюда нет `quantity` или `unit`, либо единица не поддерживается текущим nutrition flow, корректное изменение порции становится неоднозначным.

Для первой версии рекомендуется:

- показывать изменение порции только для блюд с заполненными `quantity` и `unit`;
- в первую очередь поддерживать те единицы, которые уже поддерживаются nutrition estimation: `g` и `ml`;
- для `g` и `ml` использовать небольшие абсолютные шаги изменения, а не коэффициенты;
- для остальных случаев не притворяться, что система умеет корректно менять порцию;
- действие изменения порции показывать только для блюд, у которых уже есть сохранённые nutrition metrics, пригодные для пропорционального масштабирования.

### 2.9. После item-level действий пользователь должен сразу видеть обновлённый `/recent`

После удаления, повтора или изменения порции пользователь не должен догадываться, применилось ли действие.

Следствие:

- после удаления блюда обновляется карточка записи или общий список, в зависимости от того, остались ли в записи блюда;
- после повтора пользователь получает подтверждение и обновлённый `/recent`, где новая запись находится сверху;
- после изменения порции пользователь получает обновлённый текст той же записи с новыми значениями.

## 3. Этапы реализации

### Этап 1. Добавить navigation от записи к блюдам внутри food entry

Статус: `completed`

Нужно:

- сохранить текущий список `/recent` как первый экран;
- добавить отдельный сценарий открытия конкретной `food`-записи;
- показать блюда или продукты этой записи как отдельные выбираемые элементы;
- сохранить текущее entry-level поведение для `water` и `workout`.

Ожидаемый результат этапа:

- пользователь может открыть `food`-запись из `/recent` и спуститься на уровень конкретного блюда.

Заметки при реализации:

- новый flow добавлен отдельным callback-потоком рядом с уже существующим удалением записей;
- первый экран `/recent` сохранён без смены базового сценария;
- для `water` и `workout` сохранено текущее entry-level поведение;
- экран отдельного блюда пока служит навигационной точкой и подготовкой к следующим действиям.

Фактические результаты:

- в `/recent` добавлена кнопка перехода к food-записям на текущей странице;
- пользователь может открыть список food-записей, затем конкретную запись еды и затем конкретное блюдо;
- для блюда добавлен отдельный экран с кнопкой возврата к записи;
- navigation покрыт handler-тестами без изменения существующего сценария удаления.

### Этап 2. Добавить удаление отдельного блюда из food entry

Статус: `completed`

Нужно:

- добавить действие удаления выбранного `EntryItem`;
- удалить связанные `EntryItemMetric` вместе с блюдом;
- удалить всю `Entry`, если удалён последний `EntryItem`;
- после действия обновлять экран так, чтобы пользователь сразу видел новое состояние `/recent`.

Ожидаемый результат этапа:

- пользователь может удалить одно блюдо из записи, не удаляя всю запись целиком.

Заметки при реализации:

- удаление реализовано внутри нового item-level flow, а не через старый entry-level callback;
- после удаления одной позиции сохранена текущая запись, если в ней остались другие блюда;
- если удаляется последняя позиция, пользователь остаётся внутри food-level navigation, а не выбрасывается в произвольный экран.

Фактические результаты:

- на экране блюда добавлено отдельное действие удаления с подтверждением;
- удаление одного `EntryItem` каскадно удаляет связанные `EntryItemMetric`;
- если после удаления в записи остаются блюда, пользователю показывается обновлённая запись;
- если удаляется последнее блюдо, удаляется вся `Entry`, а пользователь возвращается к списку food-записей на текущей странице;
- сценарий покрыт handler-тестами для подтверждения, частичного удаления и удаления последней позиции.

### Этап 3. Добавить повтор блюда как новой текущей food entry

Статус: `completed`

Нужно:

- добавить действие `Повторить сейчас` для выбранного блюда;
- создавать новую `food`-запись с текущим `occurred_at`;
- копировать `EntryItem` выбранного блюда в новую запись;
- копировать уже сохранённые nutrition metrics без повторного расчёта;
- если у исходного блюда нет nutrition metrics, создавать новую запись без них.

Ожидаемый результат этапа:

- пользователь может быстро повторно записать то же блюдо как новый текущий приём пищи.

Заметки при реализации:

- повтор добавлен как отдельное действие на экране блюда без дополнительного подтверждения;
- после повтора пользователь возвращается к обычному списку `/recent`, чтобы сразу увидеть новую верхнюю запись;
- для повтора не используется LLM-пересчёт и не запускается nutrition flow.

Фактические результаты:

- на экране блюда добавлено действие `Повторить сейчас`;
- повтор создаёт новую `food`-запись с текущим `occurred_at` и копией выбранного `EntryItem`;
- если у исходного блюда есть сохранённые nutrition metrics, они копируются в новую запись как есть;
- если у исходного блюда нет nutrition metrics, новая запись создаётся без них;
- сценарий покрыт handler-тестами для варианта с метриками и без метрик.

### Этап 4. Добавить inline-изменение порции фиксированным шагом

Статус: `completed`

Нужно:

- добавить для поддержанных блюд кнопки `-10 г` / `+10 г` и `-10 мл` / `+10 мл`;
- менять `quantity` только у выбранного блюда внутри существующей записи;
- пропорционально масштабировать уже сохранённые nutrition metrics без LLM-пересчёта;
- ограничить сценарий блюдами, у которых есть наблюдаемые `quantity + unit` и сохранённые nutrition metrics;
- не допускать некорректные значения порции после уменьшения.

Ожидаемый результат этапа:

- пользователь может скорректировать порцию уже сохранённого блюда небольшим фиксированным шагом и сразу увидеть обновлённый результат.

Заметки при реализации:

- изменение порции добавлено прямо на экран блюда без отдельного режима ожидания ввода;
- кнопки показываются только там, где доступны наблюдаемая порция и уже сохранённые нутриенты;
- масштабирование сделано поверх уже сохранённых `EntryItemMetric`, без обращения к LLM и без повторного nutrition flow.

Фактические результаты:

- для блюд с поддержанной порцией добавлены кнопки `-10 г` / `+10 г` и `-10 мл` / `+10 мл`;
- изменение порции доступно только для блюд с заполненными `quantity`, единицей `g` или `ml` и уже сохранёнными nutrition metrics;
- при изменении порции обновляется `quantity` выбранного блюда и пропорционально масштабируются его сохранённые `EntryItemMetric`;
- при попытке уменьшить порцию до нуля или ниже действие блокируется безопасной ошибкой без изменения записи;
- сценарий покрыт handler-тестами для показа кнопок, успешного увеличения порции и блокировки недопустимого уменьшения.
