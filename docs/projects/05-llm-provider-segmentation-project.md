# Проект: Сегментация LLM-провайдеров и пользовательских аккаунтов

Этот документ фиксирует стартовое направление для сценария, где бот поддерживает несколько LLM-провайдеров, а общий проектный провайдер остаётся доступен только ограниченной категории аккаунтов.

Цель документа:

- отделить доступ к боту от доступа к общему LLM-бюджету проекта;
- зафиксировать минимальную модель, которую можно внедрять инкрементно;
- определить порядок шагов до начала миграций и прикладочной реализации;
- дать следующему рабочему циклу понятную точку входа.

Документ не заменяет ADR. Перед изменением схемы БД и доменной модели доступа нужно отдельно зафиксировать решение в ADR.

## 1. Целевой результат

В проекте появляется разделение между:

- доступом пользователя к боту вообще;
- правом использовать основной провайдер проекта;
- правом использовать собственный провайдер пользователя;
- фактическим выбором провайдера для extraction, nutrition и conversation.

На целевом направлении система должна уметь:

- допускать пользователя в бот независимо от того, имеет ли он доступ к общему провайдеру;
- оставлять основной проектный провайдер только для категории `свои аккаунты`;
- позволять пользователю работать через собственный провайдер и собственный API-ключ;
- позволять админу в любой момент переключаться с проектного провайдера на собственный подключённый провайдер;
- позволять админу глобально отключать определённый класс провайдера для всех пользователей;
- позволять пользователю хранить несколько ключей и переключаться между ними;
- явно определять, какой провайдер был использован в каждом LLM-сценарии;
- безопасно отключать LLM-сценарии, если у пользователя нет допустимого провайдера для этого шага;
- сохранять текущую простую админ-модель из конфига и не превращать её в сложную RBAC-систему.

В ближайшую полезную версию не входят:

- автоматический биллинг чужих ключей;
- сложные тарифы и лимиты по токенам;
- self-service marketplace провайдеров;
- UI для массовой ротации секретов;
- поддержка произвольных провайдеров без заранее описанного адаптера.

## 2. Проблема текущего состояния

Сейчас в проекте:

- доступ пользователя хранится отдельно в `user_access`;
- LLM-конфигурация глобальна для всего приложения;
- extraction, nutrition и conversation используют один и тот же `OPENAI_API_KEY`;
- пользовательская категория доступа к провайдеру никак не выражена в модели данных;
- нет различия между внутренним пользователем проекта и внешним пользователем со своим ключом.
- нельзя глобально отключить провайдера как класс без изменения кода и перезапуска с новой конфигурацией;
- нельзя хранить у пользователя несколько подключений и переключать активное.

Следствие:

- невозможно безопасно открыть бота более широкому кругу пользователей, не отдавая им общий LLM-бюджет;
- нельзя подключить пользовательский ключ без архитектурного расширения фабрик и конфигурации;
- нельзя наблюдать политику выбора провайдера на уровне пользователя и конкретного вызова.

## 3. Предлагаемая продуктовая модель

### 3.1. Доступ к боту и доступ к провайдерам разделяются

Нужно сохранить отдельные решения:

- `пользователь допущен в бот`;
- `пользователь может использовать проектный LLM-провайдер`;
- `пользователь может использовать только собственный провайдер`;
- `пользователь временно не имеет доступного LLM-провайдера`.

Это означает, что текущий бинарный флаг доступа больше не должен нести всю политику LLM-использования.

### 3.2. Категория аккаунта должна быть явной

На первом целевом направлении достаточно ввести отдельную категорию аккаунта, например:

- `internal` - свои аккаунты, которым можно использовать основной проектный провайдер;
- `external` - аккаунты, которым основной проектный провайдер недоступен;
- `unassigned` - техническое состояние до admin-решения.

Важно:

- это не замена admin-прав;
- админ по-прежнему задаётся только через конфиг;
- категория аккаунта нужна именно для политики работы с LLM-провайдерами;
- категория `internal` включает админов и обычных пользователей, которым явно поставлена нужная отметка.

### 3.3. Пользовательский провайдер должен быть явно подключаемым

Для пользователя со своим провайдером минимально нужен сценарий:

- админ допускает пользователя в бот;
- пользователь или админ подключает поддержанный провайдер;
- бот хранит только необходимую информацию о подключении;
- при LLM-вызове фабрика выбирает проектный или пользовательский провайдер по политике доступа.

Дополнительно нужны сценарии:

- у пользователя может быть несколько подключений, но не больше одного ключа на пару `provider + model`;
- пользователь может переключать активное подключение среди сохранённых допустимых ключей;
- админ может для себя выбрать проектный или собственный активный провайдер;
- система учитывает глобальный запрет на класс провайдера даже при наличии сохранённого ключа.
- на первом шаге один выбранный провайдер пользователя действует сразу для всех LLM-сценариев.

### 3.4. Политика должна быть одинакова для всех LLM-слоёв

Нельзя отдельно и неявно решать доступ для:

- extraction;
- nutrition;
- conversation.

Нужен единый слой policy-resolution, который отвечает на вопрос:

- какой провайдер допустим для данного пользователя и данного сценария;
- есть ли у пользователя рабочая конфигурация;
- нужно ли отказать до начала LLM-вызова.

## 4. Рекомендуемая техническая модель

### 4.1. Не расширять `user_access` до универсального контейнера

`user_access` сейчас решает узкую задачу allow/deny. Это хороший слой для допуска к боту, и его лучше не перегружать:

- категорией аккаунта;
- списком провайдеров;
- секретами;
- политикой выбора моделей.

Рекомендуемое направление:

- `user_access` оставить слоем допуска к боту;
- провайдерную политику вынести в отдельную модель.

### 4.2. Ввести отдельный пользовательский LLM-профиль

Минимально в следующем шаге нужна отдельная сущность уровня пользователя, которая хранит:

- `user_id`;
- `account_category`;
- `provider_policy`;
- `preferred_provider`, если он задан;
- технический статус подключения.

На этом шаге не нужно финализировать точные имена таблиц и enum без ADR, но рабочее направление такое:

- отдельная таблица пользовательской LLM-политики;
- отдельная таблица подключений провайдеров пользователя;
- отдельная таблица или справочник глобальной доступности классов провайдеров.

Минимально пользовательское подключение должно позволять выразить:

- `provider`;
- `model`;
- `secret reference` или иной способ связать запись с ключом;
- `is_enabled`;
- `is_selected`;
- технический статус проверки ключа.

Инвариант первого шага:

- у одного пользователя не должно быть двух активных ключей для одной и той же пары `provider + model`.
- у пользователя выбран один активный провайдер на все LLM-сценарии.

### 4.3. Секреты пользователя не должны храниться в открытом виде в обычных текстовых полях без оговорки

До реализации нужно отдельно решить в ADR:

- допустимо ли хранение ключей в БД в зашифрованном виде;
- нужен ли внешний secret storage;
- кто именно может создавать, обновлять и удалять пользовательские ключи.

До этого решения нельзя молча добавлять `api_key` в обычную таблицу без оговорённой модели безопасности.

### 4.4. Нужен слой `provider resolver`

Фабрики `extraction`, `nutrition` и `conversation` сейчас создают клиента напрямую из глобального `Settings`.

Рекомендуемый следующий слой:

- `LLMProviderResolver`;
- вход: пользователь, LLM-сценарий, настройки приложения;
- выход: готовая provider-конфигурация или явный отказ.

Тогда фабрики перестают знать:

- внутренний ли это аккаунт;
- есть ли у пользователя собственный ключ;
- какой провайдер разрешён политикой.
- отключён ли провайдер глобально;
- использует ли админ проектный провайдер или собственное подключение.

### 4.5. Глобальная доступность классов провайдеров задаётся конфигом

Класс провайдера должен включаться и выключаться конфигурацией приложения.

Минимальное направление первого шага:

- отдельный флаг в конфиге на каждый поддержанный класс провайдера;
- resolver учитывает эти флаги до попытки выбрать пользовательское подключение;
- отключённый класс провайдера не должен использоваться ни проектным ключом, ни пользовательскими ключами.

### 4.6. При отсутствии рабочего ключа пользователь сохраняет доступ к данным

Если пользователь допущен в бот, но у него нет рабочего LLM-подключения, бот не должен блокировать доступ к уже сохранённым данным.

Минимальное направление первого шага:

- доступны команды чтения своих записей и аналитики;
- LLM-сценарии честно отказываются с понятным сообщением;
- journal-only режим допускается как fallback, если конкретная команда не требует нового LLM-вызова.

### Этап 4. Добавить минимальный admin/user workflow

Статус: `in_progress`

Нужно определить минимальный первый UX. Рекомендуемое направление:

- админ видит категорию аккаунта в списке пользователей;
- админ может перевести пользователя в `internal` или `external`;
- админ может для себя выбрать проектный или собственный активный провайдер;

- пользователь может выбрать активный ключ среди сохранённых;
- пользователь получает явное сообщение, если его категория требует собственного провайдера;
- пользователь без рабочего ключа сохраняет доступ к своим записям и аналитике.

Ожидаемый результат этапа:

- политика становится наблюдаемой и управляемой без прямого редактирования БД.

Заметки при реализации:

- В ветке уже есть первый user workflow через `/provider*`, а admin-управление категориями аккаунтов доведено до минимально наблюдаемого UX.
- Этап остаётся `in_progress`, потому что пока поддержан только `OpenAI`, а не набор пользовательских провайдеров.

Фактические результаты:

- пользователь может посмотреть текущий provider state командой `/provider`;
- пользователь может сохранить персональный `OpenAI`-ключ;
- сохранение персонального ключа обобщено до `/provider_save <provider> <model> <key>` с явным перечислением допустимых значений `provider`;
- `/provider` показывает список доступных источников: проектный ключ и сохранённые персональные подключения `provider/model`;
- для сохранённого подключения доступен отдельный экран действий `Выбрать` / `Удалить`;
- пользователь получает явный отказ, если его LLM-сценарий недоступен по текущей provider policy;
- `external`-пользователь на произвольный LLM-зависимый запрос получает подсказку сначала сохранить персональный ключ через `/provider`;
- админ видит категорию аккаунта в списке пользователей и в карточке пользователя;
- админ может перевести пользователя в `internal` или `external` из `/admin` без прямого редактирования БД.

## 6. Минимальный первый срез реализации

Чтобы не переусложнять первый рабочий шаг, рекомендуемый минимальный срез такой:

- ввести отдельную категорию аккаунта;
- оставить только два режима: `internal` и `external`;
- оставить `OpenAI` единственным поддержанным проектным провайдером первого шага;
- разрешить `internal` использовать текущий глобальный `OpenAI`-провайдер проекта;
- дать пользователю возможность сохранять собственные `OpenAI`-ключи и переключаться между ними;
- дать админу возможность выбрать для себя проектный или собственный `OpenAI`-ключ;
- добавить конфиг-флаг доступности на каждый класс провайдера;
- если у пользователя нет допустимого подключения, честно отказывать в LLM-функциях.

Это даст полезный результат без одновременного решения всех задач управления секретами через Telegram UI.

## 7. Вопросы, которые нужно закрыть до реализации

| № | Вопрос | Решение |
| --- | --- | --- |
| 1 | Какая модель хранения секретов будет принята: зашифрованная БД, внешний secret storage или другой вариант? | Шифрование в БД любым удобным способом. |
| 2 | Под “internal” понимаются только админы или админы плюс отмеченные пользователи? | Это категория, в которую всегда входят админы и обычные пользователи с явной отметкой. |
| 3 | Должен ли пользователь без собственного ключа иметь journal-only режим без conversation? | Да, чтобы при истёкшем или нерабочем ключе сохранялся доступ к своим записям и аналитике. |
| 4 | Можно ли одному пользователю иметь разные провайдеры для разных LLM-сценариев, или на первом шаге провайдер один на весь аккаунт? | На первом шаге один провайдер на все LLM-сценарии. |
| 5 | Как именно будет устроен UX глобального отключения класса провайдера: только для админа через `/admin` или ещё и через конфиг? | Доступность классов провайдеров задаётся в конфиге отдельным флагом на каждый класс. |
| 6 | Нужна ли отдельная политика для случая, когда админ выбрал собственный провайдер, но он временно недоступен? | Нет. |

## 8. Критерии завершения первого полезного шага

Первый шаг можно считать завершённым, когда:

- допуск к боту и доступ к основному провайдеру разделены в модели;
- у пользователя есть явная account category;
- `internal` пользователи продолжают работать без регрессии;
- external-пользователь не может случайно тратить общий провайдерный бюджет;
- админ может переключаться между проектным и собственным поддержанным провайдером;
- система умеет отключать класс провайдера через конфиг;
- пользователь может хранить несколько ключей и выбирать активный для пары `provider + model`;
- пользователь без рабочего ключа сохраняет доступ к своим записям и аналитике;
- код выбора провайдера централизован;
- пользователь получает понятный отказ, если его провайдер не настроен;
- документация и тесты обновлены вместе с кодом.
