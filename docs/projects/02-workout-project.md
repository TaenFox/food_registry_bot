# Проект: Workout Layer поверх unified journal

Этот документ фиксирует согласованное направление развития функциональности тренировок.

Цель документа:

- сохранить результат обсуждения в репозитории;
- отделить product scope тренировок от уже реализованного nutrition scope;
- дать следующий понятный шаг для новой сессии Codex;
- не подменять этим документом ADR по схеме БД, extraction contract и aggregation rules.

Если очередной этап меняет модель данных, пользовательский контракт journal flow, правила агрегации или conversational contract вокруг тренировок, перед реализацией это нужно зафиксировать отдельным ADR.

## 1. Целевой результат

В проекте появляется отдельный factual workout layer, встроенный в существующий unified journal.

На целевом направлении система должна уметь:

- позволять пользователю включить или не включать workout-функциональность для своего аккаунта;
- принимать тренировку как отдельный journal fact;
- сохранять тренировку в PostgreSQL как `entry_type = workout`;
- возвращать пользователю короткое подтверждение сохранения;
- позже использовать workout facts как вход для дневных summary и nutrition guidance.

При этом тренировки на текущем направлении рассматриваются именно как factual journal functionality, а не как отдельный conversational coach.
По умолчанию workout-функциональность должна быть выключена, пока пользователь явно её не включил.

## 2. Уже принято

Ниже перечислены решения, которые уже следуют из существующих ADR и проектных документов.

### 2.1. Тренировки остаются частью unified journal

Тренировка не оформляется как отдельная подсистема со своим независимым жизненным циклом.

Базовая договорённость остаётся такой:

- тренировка сохраняется как `entry`;
- общие сценарии добавления, удаления и пересчёта должны оставаться концептуально едиными для еды, воды и тренировок;
- специализированные workout-поля допустимы, если они расширяют общую модель, а не ломают её.

Связанный ADR:

- [ADR-002](/Users/pmokeev/Desktop/Projects/food_registry_bot/docs/adr/ADR-002-unified-journal-model.md:1)

### 2.2. Workout layer нужен раньше trainer coach

Пока в системе нет целостного factual workout layer, не стоит вводить отдельный `trainer coach`.

Порядок развития должен быть таким:

- сначала factual workout logging;
- затем, при необходимости, workout-aware nutrition context;
- только потом отдельные conversational сценарии, если они действительно нужны.

### 2.3. Тренировки не должны сразу тащить сложную фитнес-модель

Первый шаг не должен требовать:

- каталога упражнений;
- хранения подходов, повторений и весов для всех сценариев;
- periodized training planner;
- интеграций с wearable apps;
- OCR-пайплайна для любых workout screenshots.

Иначе проект слишком рано уйдёт в фитнес-трекер вместо полезного journal-layer.

## 3. Основная продуктовая рамка

### 3.1. Что считать первой полезной функциональностью

Первой полезной функциональностью тренировок считается не аналитика и не коучинг, а надёжное сохранение workout-факта в дневнике.

Минимально полезный результат:

- у пользователя есть явная настройка, использует ли он вообще тренировочный слой;
- пользователь может явно записать тренировку;
- система не путает такую запись с едой, водой или обычным разговором;
- тренировка сохраняется как наблюдаемый факт;
- сохранённый факт можно позже использовать в отчётах и nutrition guidance.

При этом безопасное поведение по умолчанию:

- если workout-функциональность не включена, bot не должен молча сохранять тренировки;
- rollout workout-сценариев можно делать без изменения поведения для пользователей, которым это не нужно.

### 3.2. Что не входит в первый целостный шаг

В ближайший первый шаг не входят:

- разбор сложных скриншотов тренировок;
- автоматическое извлечение всех упражнений по фото;
- отдельные workout summary screens;
- долгосрочная аналитика прогресса;
- планирование тренировок;
- отдельный `trainer coach`.

## 4. Приоритетные пользовательские сценарии

Ниже перечислены сценарии в рекомендуемом порядке.

### 4.1. Явная запись тренировки текстом

Примеры:

- `тренировка: бег 40 минут`;
- `сегодня была силовая 50 минут`;
- `велотренажёр 30 минут, средняя нагрузка`.

Ожидаемое поведение:

- routing распознаёт намерение как `workout journal`;
- extraction выделяет минимально нужную структуру;
- система сохраняет тренировку;
- пользователь получает короткое подтверждение.

Это рекомендуемый первый этап реализации.

### 4.2. Использование workout-факта в nutrition context

Примеры:

- `что лучше съесть после сегодняшней тренировки?`;
- `как скорректировать ужин после кардио?`;
- `нужно ли сегодня добирать белок после силовой?`

Ожидаемое поведение:

- `nutrition coach` по-прежнему остаётся nutrition-first;
- но factual context может включать уже сохранённые workout entries;
- тренировки влияют на интерпретацию дня только через factual layer, а не через свободные предположения модели.

Это рекомендуемый второй этап после появления первого factual workout слоя.

### 4.3. Скриншоты тренировок как journal input

Примеры:

- скриншот отчёта из fitness app;
- скриншот беговой тренировки;
- mixed screenshot с duration, distance, calories.

Ожидаемое поведение:

- система умеет принимать screenshot как источник workout-факта;
- при нескольких screenshots одного workout приоритет по calorie fact отдаётся фирменному приложению производителя аксессуара или тренажёра;
- screenshots из других приложений на текущем шаге используются скорее как вспомогательный контекст для характера тренировки;
- состав упражнений на этом шаге не сохраняется;
- полезный новый сохраняемый metric этого этапа - factual calories тренировки, если они явно присутствуют;
- граница с conversational и food-photo сценариями остаётся консервативной;
- extraction contract для workout screenshot вводится отдельно и проверяемо.

Это отдельный поздний этап, а не часть первого инкремента.

## 5. Рекомендуемая техническая рамка

### 5.1. Сначала нужен workout factual contract, а не полная фитнес-схема

Перед кодом первого этапа стоит зафиксировать ADR для минимального workout contract.

В нём нужно решить:

- где и как хранится пользовательская настройка включения workout-функциональности;
- какие поля считаются обязательными для первой сохранённой тренировки;
- что хранится как структурированный факт, а что пока остаётся только в `source_text`;
- нужны ли workout-specific metrics на первом шаге;
- как routing отличает workout-log от nutrition-question про тренировку.

### 5.2. Первый слой должен быть минимальным и обратимым

Рекомендуемое направление для первого шага:

- выбрать маленький набор полей, без которых запись тренировки теряет смысл;
- не вводить богатую иерархию сущностей раньше необходимости;
- сохранять исходный пользовательский текст, чтобы можно было безопасно расширить модель позже;
- проектировать миграции так, чтобы последующее уточнение workout-модели не ломало уже сохранённые данные.

### 5.3. Workout goals не считаются ожидаемым направлением по умолчанию

На текущем направлении не стоит предполагать, что боту нужен отдельный слой workout goals или автоматическая корректировка nutrition goals из-за тренировок.

Если позже появится конкретный и полезный кейс, это нужно будет обсуждать отдельно как новую продуктовую потребность, а не как автоматическое продолжение workout layer.

### Этап 0. Проектная фиксация направления

Статус:

Результат:

- подтверждено, что `trainer coach` пока не вводится.

### Этап 1. Text-first workout logging

Статус:

- `[x]` выполнен

Цель:

- дать пользователю возможность явно записывать тренировку текстом.

Входит в этап:

- пользовательская настройка включения workout-функциональности с состоянием `off` по умолчанию;
- routing для workout journal intent;
- минимальный extraction contract для text workout input;
- сохранение workout entry в БД;
- пользовательское подтверждение сохранения;
- тесты и обновление `docs/user-functions.md`.

Не входит в этап:

- screenshot parsing;
- goal adjustments;
- workout-aware coach;
- продвинутая exercise-level модель.

Связанный ADR:

- [ADR-027](/Users/pmokeev/Desktop/Projects/food_registry_bot/docs/adr/ADR-027-opt-in-text-workout-logging.md:1)

### Этап 2. Workout-aware factual context

Статус:

- `[x]` выполнен

Цель:

- начать использовать сохранённые workout facts в nutrition-related интерпретации дня.

Входит в этап:

- чтение workout entries дня в factual context;
- обновление `nutrition coach` contract при наличии workout layer;
- тесты на использование тренировочного контекста без превращения агента в `trainer coach`.

Не входит в этап:

- отдельный workout coach;
- изменение goals и snapshots.

Связанный ADR:

- [ADR-028](/Users/pmokeev/Desktop/Projects/food_registry_bot/docs/adr/ADR-028-workout-aware-factual-context-for-nutrition-coach.md:1)

### Этап 3. Workout screenshots

Цель:

- добавить безопасный и наблюдаемый screenshot-based input для тренировок.

Входит в этап:

- отдельный multimodal workout extraction contract;
- source-priority правила между несколькими screenshots одного workout;
- сохранение factual workout calorie metric при достаточной уверенности;
- правила routing для screenshot input;
- тесты на смешанные и неоднозначные сценарии.

Текущий статус этапа:

- реализован первый узкий подэтап: `single-screenshot workout logging`;
- бот умеет принять один screenshot тренировки и сохранить `workout entry`;
- если на screenshot явно видны калории тренировки, они сохраняются как factual metric `workout_calories`;
- состав упражнений и multi-image merge пока не реализованы.

Не входит в этап:

- сохранение exercise-by-exercise состава тренировки;
- OCR полного списка упражнений как самостоятельной цели;
- derived calorie corrections между разными приложениями.

Связанный ADR:

- [ADR-029](/Users/pmokeev/Desktop/Projects/food_registry_bot/docs/adr/ADR-029-workout-screenshot-priority-and-calorie-metric.md:1)

## 7. Критерий хорошего следующего шага

Хорошим следующим шагом считается такой инкремент, который:

- оставляет проект в проверяемом состоянии;
- не требует сразу строить полноценный фитнес-трекер;
- добавляет новый factual capability, а не только обсуждение;
- сохраняет возможность позже уточнить workout-модель без переписывания всей схемы.
