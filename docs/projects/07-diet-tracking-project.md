# Проект: Сопровождение диет

Этот документ фиксирует предварительное направление для сценария, где бот умеет сопровождать поддержанные диеты и учитывать их в уже существующем nutrition feedback flow.

Цель документа:

- зафиксировать первую обязательную поддержанную диету `низкопуриновая`;
- сохранить возможность добавления новых диет через код и миграции;
- опереться на уже существующую item-level metric model, а не придумывать новый storage без необходимости;
- опереться на уже существующие механизмы обработки неполных исторических данных;
- дать следующему рабочему циклу понятную точку входа для ADR и реализации.

Документ не заменяет ADR. Перед изменением схемы БД, модели пользовательских настроек и write/report contract нужно отдельно зафиксировать решение в ADR.

## 1. Целевой результат

В проекте появляется поддержка диетического сопровождения.

На целевом направлении система должна уметь:

- обязательно поддерживать как минимум одну диету: `низкопуриновая`;
- позволять разработчику добавлять новые поддержанные диеты через код, миграции и domain-конфигурацию;
- позволять пользователю включать каждую поддержанную диету отдельно;
- сохранять числовую оценку по шкале `1-10` для каждого отдельного блюда и для каждой включённой диеты, где:
  - `1` - совсем не соответствует диете;
  - `5` - нейтрально;
  - `10` - максимально соответствует диете;
- учитывать воду в diet scoring:
  - вода может сохраняться как полезный item для конкретной диеты;
  - для `низкопуриновой` диеты вода должна повышать средний бал;
- строить один post-entry comment после записи еды так, чтобы он учитывал все включённые диеты пользователя;
- передавать в conversational LLM context информацию о включённых диетах пользователя;
- убрать пользовательский префикс `Нутрициолог` у этого комментария;
- считать среднее значение diet-метрики за период в `/report`;
- в `/recent` показывать средний diet score по приёму пищи;
- не вводить по diet-метрике пользовательские цели и не смешивать её с `daily_goal_snapshots`.

В первую полезную версию не входят:

- медицинские рекомендации и лечебные протоколы;
- автоматическое переключение диеты по расписанию;
- длинные объяснения диеты после каждой записи;
- отдельные дневные цели по diet-метрикам;
- обязательный backfill старых записей после включения новой диеты;
- отдельный coach-диалог про подбор диеты.

## 2. Актуальная база в коде

Сейчас в проекте уже есть несколько важных опорных механизмов:

- поддерживаемые nutrition metrics хранятся как `entry_item_metrics`;
- новые метрики уже добавляются разработчиком через `supported_metrics` и миграции;
- `entry_item_metrics` уже привязаны к отдельному `entry_item`, а не к записи целиком;
- post-entry comment хранится в `entries.llm_comment` и строится как отдельный шаг после successful food write flow;
- пользовательский префикс `Нутрициолог` сейчас добавляется на уровне Telegram handler, а не является обязательной частью prompt contract;
- `/today` и `/report` уже умеют честно жить с неполными данными:
  - неполные food entries исключаются из nutrition aggregation;
  - пользователю показываются пометки о неполных данных;
  - в period report уже есть `incomplete_food_day_count` и `incomplete_water_day_count`;
- старые записи без части метрик уже не считаются фатальной ошибкой модели данных.

Следствие:

- новая диета не обязана требовать отдельное хранилище метрик, если существующий item-level metric storage покрывает сценарий;
- расширение post-entry comment можно делать поверх уже существующего `entries.llm_comment`, если не ломать его factual contract;
- исторические записи без diet-оценки допустимы и хорошо совпадают с уже существующей логикой неполных данных.

## 3. Рекомендуемая продуктовая модель

### 3.1. Первая обязательная диета - низкопуриновая

На первом шаге проект должен реально поддерживать одну конкретную диету, а не только абстрактный framework.

Первая обязательная диета:

- `низкопуриновая`.

При этом реализация должна оставаться расширяемой к новым диетам без пересмотра базовой модели хранения и пользовательских настроек.

### 3.2. Поддержанные диеты задаются разработчиком

Пользователь не создаёт свои произвольные диеты.

Минимально каждая поддержанная диета должна иметь:

- стабильный `code`;
- display name;
- короткое пользовательское описание;
- критерии оценки блюд;
- prompt/rubric-конфигурацию или иной способ задать правила оценки.

Добавление новой диеты должно быть developer-managed шагом:

- код;
- миграция справочника и метрик;
- тесты;
- при необходимости обновление пользовательской документации.

### 3.3. Пользователь может включать каждую поддержанную диету отдельно

Система должна поддерживать несколько диет и позволять пользователю независимо включать каждую из них.

Следствие:

- одна и та же запись еды может оцениваться сразу по нескольким включённым диетам;
- одна и та же историческая позиция записи может иметь несколько diet metrics;
- `/settings` должен выражать именно включение и выключение диет, а не выбор единственной активной диеты.

### 3.4. Diet score относится к отдельному блюду

Пользователь явно сформулировал ожидаемый уровень оценки: не запись целиком, а отдельное блюдо.

Следствие:

- diet score хранится на уровне `entry_item`;
- один `entry_item` может иметь несколько diet-оценок;
- multi-item запись еды может содержать блюда с разными оценками;
- агрегаты по периоду должны строиться поверх item-level оценок.

Для воды решение уже согласовано:

- вода тоже получает отдельную diet-оценку как item внутри water entry;
- для `низкопуриновой` диеты вода считается полезным приёмом и должна улучшать средний бал.

### 3.5. Diet metrics должны по возможности использовать существующий metric storage

Текущая система уже хранит расширяемые item-level метрики через:

- `supported_metrics`;
- `entry_item_metrics`.

Поэтому на текущем этапе нет достаточного основания заранее выносить diet score в отдельное хранилище только потому, что это диетическая оценка.

Рекомендуемое направление для обсуждения и ADR:

- diet scores хранятся как новые developer-managed metric codes в существующем `supported_metrics`;
- значения сохраняются в существующем `entry_item_metrics`;
- diet metric code должен явно указывать на конкретную диету.

Пример направления именования:

- `low_purine_score`;
- далее по тому же правилу для новых диет.

Это сохраняет консистентность модели:

- nutrition metrics и diet metrics живут в одном item-level storage;
- новые диеты добавляются тем же способом, что и новые поддержанные метрики;
- старые записи без diet score естественно остаются просто неполными для соответствующего diet-сценария.

### 3.6. Post-entry comment должен стать общим nutrition-and-diet comment

Сейчас в проекте уже есть один post-entry comment, который:

- строится после successful food write flow;
- хранится в `entries.llm_comment`;
- не влияет на сам факт сохранения записи.

Рекомендуемое направление:

- не вводить второй параллельный comment-блок для диет;
- убрать пользовательский префикс `Нутрициолог` из рендера comment;
- расширить prompt существующего post-entry comment так, чтобы он учитывал включённые диеты пользователя;
- diet-aware расширение comment выполняется только через LLM;
- сам comment остаётся единым коротким текстом, а не набором отдельных сообщений по каждой диете.

Это даёт более естественный пользовательский контракт:

- factual summary и nutrition deltas остаются как сейчас;
- comment становится более умным и учитывает diet constraints;
- пользователь не получает два конкурирующих LLM-комментария после одной записи.

### 3.7. Conversational context тоже должен учитывать включённые диеты

Diet tracking не должен ограничиваться только write flow и `/report`.

Если пользователь ведёт диалог с nutrition coach, в conversational context должна передаваться информация о включённых диетах пользователя.

Следствие:

- диалоговые ответы про выбор еды, планирование дня, продукты и воду должны учитывать активные diet constraints;
- это относится к обычному conversational reply, а не только к post-entry comment;
- включённые диеты становятся частью user context для LLM, но не подменяют factual day data.

### 3.8. Исторические записи без diet score допустимы

Если пользователь уже вёл журнал, а потом включил диету, старые записи и блюда без diet-метрик считаются допустимым историческим состоянием.

Следствие:

- старые записи не требуют обязательного backfill;
- новые diet metrics начинают появляться только у новых записей после включения диеты;
- `/report` должен считать diet-агрегацию только по тем блюдам, где нужная diet-метрика присутствует.

Это хорошо совпадает с уже существующей реализацией:

- `daily summary` уже умеет исключать неполные записи из агрегатов;
- `period report` уже считает неполные дни отдельно;
- админский обзор уже показывает incomplete food entries.

На первом шаге рекомендуется использовать ту же общую идею:

- отсутствие diet score у старых блюд не ошибка;
- это просто неполные исторические данные для соответствующего diet-блока.

### 3.9. В `/settings` нужен отдельный сценарий включения диет

Выбор диет не должен прятаться под обычные toggles показа nutrition metrics.

Рекомендуемый первый UX:

- в `/settings` появляется отдельный блок `Диеты`;
- каждая поддержанная диета показывается отдельно;
- для каждой диеты пользователь видит статус `включена` или `выключена`;
- первая обязательная диета в системе: `низкопуриновая`.

### 3.10. В `/recent` показывается средний diet score по приёму пищи

Для `recent` не нужно показывать diet score на уровне конкретного блюда.

Согласованное направление:

- в списке и entry-level экране `/recent` можно показывать средний diet score по приёму пищи;
- при переходе к конкретному блюду его оценка не показывается;
- средний score приёма пищи строится как агрегат по item-level diet metrics этой записи.

### 3.11. Diet score в отчёте живёт отдельно от целей

Diet score не должен вести себя как calories/protein/water goal metric.

Следствие:

- для него не появляется поле в `user_goal_preferences`;
- для него не появляется колонка в `daily_goal_snapshots`;
- `/report` показывает его в отдельном блоке;
- блок `Цели` в `/report` не учитывает diet score.

### 3.12. Среднее значение в `/report` лучше считать по оценённым блюдам

Для diet score на первом шаге рекомендуется считать среднее по всем оценённым `entry_item` периода для конкретной диеты.

Причины:

- score относится к блюду;
- это совпадает с уже существующей item-level моделью метрик;
- это не требует отдельной таблицы period summaries.

При этом в отчёте нужно явно показывать опору расчёта:

- среднее значение;
- количество блюд;
- количество дней, в которых были diet-evaluated блюда;
- при наличии старых данных без оценки система считает только по тем блюдам, где соответствующая diet-метрика уже есть.

## 4. Рекомендуемая техническая рамка

### 4.1. Нужен отдельный справочник поддержанных диет

Рекомендуемое направление:

- отдельная таблица или seed-справочник `supported_diets`;
- developer-managed наполнение;
- стабильные коды для ссылок из настроек и из diet metric codes.

Минимально справочник должен позволять выразить:

- `code`;
- `name`;
- `is_enabled`;
- служебные поля для prompt/rubric-конфигурации, если они не остаются только в коде.

### 4.2. Пользовательские настройки включения диет должны храниться отдельно или расширять preferences

На первом шаге не нужно превращать `user_summary_preferences` в контейнер для всех будущих health protocols без необходимости.

Но допустимы два направления, которые нужно выбрать в ADR:

- добавить в `user_summary_preferences` отдельные флаги включения для поддержанных диет;
- ввести отдельную сущность пользовательских diet preferences.

Предварительная рекомендация:

- если на первом шаге поддерживается только `низкопуриновая` и ещё 1-2 диеты в обозримом росте, можно начать с простых флагов в preferences;
- если ожидается быстрый рост количества диет и их пользовательских параметров, лучше сразу вынести их в отдельную таблицу.

### 4.3. Нужен отдельный сервис diet evaluation, но не обязательно отдельное хранилище метрик

Текущие слои `extraction`, `nutrition` и `conversation` уже разведены.

Для diet support рекомендуется добавить отдельный слой, например:

- `DietEvaluationService`;
- `SupportedDietRepository`.

Такой слой должен отвечать за:

- выбор включённых диет пользователя;
- подготовку factual input по сохранённым `entry_item`;
- вызов LLM evaluator;
- сохранение diet scores через существующий metric storage;
- безопасный fallback при технической ошибке.

Отдельный репозиторий может понадобиться не для самих scores, а только для дополнительных diet-specific сущностей, если они действительно появятся после ADR.

### 4.4. Conversational context должен расшириться списком включённых диет

Текущий nutrition coach уже получает `factual_context`.

Следующий шаг должен явно добавить в этот context информацию о включённых диетах пользователя.

Минимальное направление:

- в context builder добавляется список включённых diet codes и их display names;
- conversational prompt использует этот список как пользовательские ограничения;
- post-entry comment использует тот же diet-aware context, а не отдельный несвязанный источник.

### 4.5. Write flow должен расширять существующий safe contract

Рекомендуемый порядок для `food`:

1. extraction;
2. сохранение journal entry и entry_items;
3. nutrition estimation и сохранение nutrition metrics;
4. diet evaluation для включённых диет пользователя на уровне `entry_item`;
5. построение одного post-entry comment с учётом nutrition context и включённых диет;
6. ответ пользователю.

Важно:

- если у пользователя не включена ни одна диета, diet evaluation пропускается;
- diet evaluation не должен подменять factual сохранение записи;
- расширение post-entry comment не должно ломать текущий safe fallback.

Предварительная рекомендация для обсуждения:

- `food` запись не должна откатываться из-за ошибки diet evaluation;
- если diet metrics или общий comment не удалось получить, запись всё равно сохраняется;
- пользователь получает обычный confirmation response без отдельной ошибки diet-слоя.

### 4.6. Для diet score не нужны goal snapshots

Это отдельное архитектурное решение, которое важно не потерять до реализации.

На этом направлении:

- score - это evaluative signal;
- goal - это user target;
- diet tracking не требует daily target snapshots.

Если позже появится отдельный сценарий `минимально желаемый средний score`, его нужно обсуждать как новую функциональность, а не как скрытое продолжение текущего шага.

## 5. Инкрементальный план реализации

### Этап 1. Зафиксировать ADR по diet registry, metric codes и comment contract

Статус: `planned`

Нужно определить:

- отдельный ли это справочник `supported_diets`;
- где хранятся флаги включения диет пользователя;
- какие metric codes появляются для первой диеты `низкопуриновая`;
- как включённые диеты попадают в conversational context;
- как существующий post-entry comment учитывает включённые диеты;
- убирается ли пользовательский префикс `Нутрициолог` полностью;
- откатывает ли ошибка diet evaluation сохранение записи;
- как `/report` считает и показывает исторические блюда без diet score;
- как `/recent` показывает средний diet score по записи без показа item-level оценки на экране блюда.

Ожидаемый результат этапа:

- согласованный ADR без спорных решений перед миграциями.

### Этап 2. Добавить доменную модель и миграции

Статус: `planned`

Нужно:

- добавить справочник поддержанных диет;
- добавить хранение пользовательских флагов включения диет;
- добавить новые supported metrics для `низкопуриновой` диеты;
- подготовить простые обратимые миграции;
- засеять хотя бы одну реальную диету `низкопуриновая`.

Ожидаемый результат этапа:

- в БД можно выразить supported diets, user diet settings и item-level diet metrics.

### Этап 3. Добавить `/settings`, item-level diet evaluation и общий post-entry comment

Статус: `planned`

Нужно:

- показать пользователю поддержанные диеты и их текущий статус в `/settings`;
- дать UX включения и выключения каждой диеты;
- передавать включённые диеты в conversational context;
- после успешной записи выполнять diet evaluation для включённых диет на уровне `entry_item`;
- сохранять diet scores в существующем metric storage;
- убрать пользовательский префикс `Нутрициолог` из post-entry comment;
- расширить prompt comment так, чтобы он учитывал включённые диеты пользователя.
- показывать средний diet score по записи в `/recent`.

Ожидаемый результат этапа:

- пользователь может включить диету и сразу увидеть обновлённый comment и новые diet-оценки для новых блюд.

### Этап 4. Добавить diet-блок в `/report`

Статус: `planned`

Нужно:

- построить period aggregation по item-level diet metrics;
- поддержать первую диету `низкопуриновая`;
- показать средний score за период;
- показать количество блюд и дней в расчёте;
- честно учитывать наличие старых блюд без оценки;
- не смешивать этот блок с goal hit и nutrition tolerance.

Ожидаемый результат этапа:

- `/report` показывает отдельный diet-блок без появления новых целей и без требования backfill старых записей.
