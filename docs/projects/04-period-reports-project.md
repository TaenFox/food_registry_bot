# Проект: Аналитические отчёты за период

Этот документ фиксирует согласованное направление развития пользовательских аналитических отчётов за период.

Цель документа:

- сохранить текущие продуктовые договорённости в репозитории;
- зафиксировать минимальный полезный UX до реализации;
- отделить первую полезную версию отчётов от более тяжёлой аналитики;
- дать инкрементальный план, по которому можно продолжать обсуждение и реализацию.

Документ не заменяет ADR. Если следующий этап меняет доменную модель, схему БД, правила исторического расчёта целей или архитектурную границу summary/reporting слоя, перед реализацией это нужно зафиксировать отдельным ADR.

## 1. Целевой результат

В проекте появляется отдельная пользовательская команда `/report`, которая показывает аналитический отчёт за выбранный период.

На ближайшем целевом направлении система должна уметь:

- принимать отдельную команду `/report`;
- быстро строить отчёт за типовые периоды без ручного ввода дат;
- позволять быстро переключать период одной циклической inline-кнопкой под уже показанным отчётом;
- показывать средние значения только по тем дням, где реально есть данные;
- явно показывать, по скольким дням считаются показатели;
- показывать попадание в цели не по строгому равенству, а по настраиваемому допуску;
- отдельно открывать детализацию по заметным записям пищи для периода.
- отдельно открывать срез динамики по подпериодам внутри выбранного периода.

На текущем направлении в первую версию не входят:

- графики;
- сравнение двух периодов;
- LLM-комментарии к отчёту;
- отдельная витрина “вся статистика по дням” внутри основного ответа;
- пользовательский произвольный диапазон дат;
- новая таблица предрассчитанных периодных summary, если текущий слой позволяет начать без неё.

## 2. Уже принято

Ниже перечислены решения, уже согласованные в обсуждении.

### 2.1. Отчёт должен быть отдельной командой

Периодная аналитика не встраивается в `/today` и не прячется только в `/files`.

Согласованная точка входа:

- отдельная команда `/report`.

Причина:

- дневной и периодный сценарии остаются разделены;
- пользовательский вход ясен и не перегружает уже существующие команды.

### 2.2. Основной отчёт должен быть коротким

Основной ответ `/report` не должен превращаться в длинную статистическую выкладку.

В первую версию основного ответа входят:

- выбранный период;
- число календарных дней в периоде;
- число дней с данными по каждому слою;
- средние значения по дням с данными;
- попадание в цели;
- вода и тренировки;
- краткая пометка о неполных днях, если они есть.

Из основного ответа исключаются:

- суммы метрик за весь период;
- длинная дневная разбивка;
- статистические термины, требующие отдельного объяснения.

### 2.3. Средние считаются только по дням с данными

Пользователь явно запросил, чтобы средние значения не размывались пустыми днями.

Следствие:

- в отчёте нужно явно показывать число дней с данными;
- среднее по еде считается по дням, где есть данные по еде;
- среднее по воде считается по дням, где есть данные по воде;
- тренировочные показатели считаются по тренировочным дням или тренировочным событиям в зависимости от конкретной метрики.

### 2.4. Нужно честно показывать полноту данных

Если часть food entries не имеет полного набора nutrition metrics, отчёт не должен маскировать это как точный результат.

Следствие:

- отчёт должен уметь показывать число полных и неполных дней по еде;
- попадание в nutrition goals должно считаться только по тем дням, где данные достаточны для такой проверки;
- пользователь получает краткую текстовую пометку о неполных днях.

### 2.5. `p80` не нужно показывать в основном отчёте

Идея с `p80` признана потенциально полезной, но слишком перегружающей основной ответ.

Согласованное решение:

- не показывать `p80` в основном `/report`;
- если нужен анализ “что выбивалось”, выводить его в отдельной детализации;
- при необходимости использовать `p80` как внутренний порог отбора, но не как обязательный пользовательский термин.

### 2.6. Детализация заметных записей пищи открывается отдельно

Пользователю нужен ответ не только “есть выбросы”, но и “какие именно записи были больше обычного”.

Согласованное направление:

- под основным отчётом есть отдельная inline-кнопка детализации;
- в детализации показываются конкретные записи, а не только статистический порог;
- формулировка должна быть нейтральной, без оценочности;
- согласованное пользовательское название: `Заметные записи пищи`.

### 2.7. Детализация должна переключаться по одной метрике за раз

Сообщение с детализацией не должно пытаться одновременно показать все метрики.

Согласованное направление:

- по нажатию кнопки открывается список по одной метрике;
- в начале или в конце сообщения показывается список доступных метрик;
- доступными считаются только метрики, которые:
  - включены у пользователя в summary settings;
  - имеют записи в выбранном периоде;
- текущая показанная метрика должна быть явно отмечена в этом списке;
- в сообщении есть кнопка `Следующая метрика`;
- по нажатию `Следующая метрика` текст и кнопки обновляются циклически для следующей метрики;
- в списке показывается не больше `10` записей;
- у каждой записи обязательно показывается дата;
- в сообщении есть кнопка `Закрыть`, которая удаляет это сообщение.

### 2.8. Быстрое переключение периода должно быть одной циклической кнопкой

Под отчётом должна быть циклическая inline-кнопка, чтобы пользователь мог быстро переключать период без повторного ввода команды и без перегрузки клавиатуры.

Согласованное направление:

- одна кнопка `Следующий период`;
- периоды перебираются циклически;
- пользовательский произвольный период не вводится;
- рядом с основной кнопкой должна быть кнопка удаления сообщения.

Текущий рекомендуемый набор периодов:

- `8 дней`;
- `16 дней`;
- `32 дня`.

### 2.9. В отчёте показываются только включённые метрики

Отчёт не должен показывать показатели, которые пользователь уже выключил в `summary settings`.

Следствие:

- основной `/report` показывает только включённые метрики;
- детализация `Заметные записи пищи` показывает только включённые метрики, у которых есть записи;
- вода и nutrition-метрики подчиняются тем же пользовательским настройкам видимости.

### 2.10. Попадание в цель считается по допуску, а не по строгому равенству

Строгое равенство почти не имеет продуктовой ценности.

Согласованное направление:

- день считается выполненным, если фактическое значение попадает в диапазон вокруг цели;
- размер диапазона задаётся пользователем как отдельная настройка;
- в отчёте нужно явно показывать, что цели считаются с допуском.

Пример:

- цель `1800 ккал`;
- допуск `10%`;
- день считается выполненным, если факт лежит в диапазоне `1620-1980`.

### 2.11. Настройка допуска к цели должна быть пользовательской

На текущем направлении это не захардкоженная константа, а пользовательская настройка.

Для первой версии предпочтительно:

- не свободный ввод;
- а небольшой фиксированный набор значений.

Предварительно согласованный вид:

- `5%`;
- `10%`;
- `15%`;
- `20%`.

Согласованное место этой настройки:

- `/settings`.

Допустимо изменить текущий порядок и форму мозаики кнопок в `settings`, если это упрощает UX.

### 2.12. Percentile-порог для заметных записей тоже должен быть пользовательской настройкой

Порог отбора заметных записей не должен быть жёстко зашит в коде без возможности подбора.

Согласованное направление:

- percentile-порог хранится как пользовательская настройка;
- настройка живёт в `/settings`;
- поддерживаются фиксированные значения с шагом `5%`;
- допустимый диапазон: от `70%` до `95%`.

Причина:

- полезный порог нужно подбирать на реальных пользовательских данных;
- пользователю важнее список релевантных записей, чем единый “идеальный” percentile для всех.

### 2.13. Для отчёта нужен отдельный срез динамики

Помимо основного summary и заметных записей пользователь хочет видеть короткую динамику по подпериодам.

Согласованное направление:

- под основным отчётом есть отдельная кнопка `Динамика`;
- динамика показывается отдельным сообщением;
- в сообщении показывается только одна метрика за раз;
- доступны только метрики, которые:
  - включены у пользователя в summary settings;
  - имеют данные в выбранном периоде хотя бы в одном подпериоде;
- в сообщении есть кнопка `Следующая метрика`;
- по нажатию `Следующая метрика` текст и кнопки обновляются циклически;
- в сообщении есть кнопка `Закрыть`, которая удаляет сообщение.

### 2.14. Динамика строится по подпериодам длиной 4 дня

Согласованное направление:

- полный период делится на подпериоды по `4` календарных дня;
- базовые периоды `/report` подстраиваются под эту кратность;
- поэтому в быстром переключении используются `8`, `16` и `32` дня;
- подпериоды в сообщении динамики показываются в хронологическом порядке: от более старого к более новому.

### 2.15. В динамике нужно честно показывать дни с данными внутри подпериода

Для каждой строки динамики нужно показывать не просто среднее, а ещё и опору этого среднего.

Согласованное направление:

- если в подпериоде есть данные, рядом со значением показывается число дней с данными в формате `(N/4 дней)`;
- если в подпериоде нет данных по текущей метрике, строка всё равно показывается;
- для такого подпериода выводится текст `нет данных`.

## 3. Продуктовая рамка первой версии

### 3.1. Что считать первой полезной функциональностью

Первой полезной функциональностью считается не полный аналитический кабинет, а короткий и честный Telegram-отчёт по периоду.

Минимально полезный результат:

- пользователь отправляет `/report`;
- получает понятный отчёт за типовой период;
- видит, сколько дней реально легло в расчёт;
- может быстро переключить период одной кнопкой;
- понимает попадание в цели по допуску, а не по строгому равенству;
- при желании уходит в отдельную детализацию заметных записей пищи;
- при желании открывает отдельный срез динамики по подпериодам.

### 3.2. Что не входит в первый целостный шаг

В ближайший первый целостный шаг не входят:

- сохранённые пользовательские пресеты отчётов;
- экспорт period report в отдельный файл;
- сравнение `этот период` против `предыдущего периода`;
- отдельные percentile/median-блоки в основном ответе;
- автоматические текстовые выводы “почему так получилось”;
- произвольный пользовательский период;
- новая materialized summary модель без подтверждённой необходимости.

## 4. Основной пользовательский сценарий

### 4.1. Базовый просмотр отчёта

Пользователь:

- отправляет `/report`.

Система:

- строит отчёт за дефолтный период;
- показывает компактный текстовый ответ;
- добавляет inline-кнопки циклического переключения периода, детализации, динамики и удаления сообщения.

Ожидаемый вид ответа на текущем направлении:

```text
Отчёт: 19.05.2026-25.05.2026
Дней в периоде: 8
Дней с данными по еде: 5

Среднее по дням с данными
- калории: 2 140 ккал
- белки: 116 г
- жиры: 66 г
- углеводы: 221 г
- клетчатка: 21 г
- вода: 1 780 мл

Цели считаются с допуском 10%.
- калории: 4 из 5 дней
- белки: 5 из 5 дней
- жиры: 3 из 5 дней
- углеводы: 4 из 5 дней
- вода: 3 из 6 дней

Есть 1 неполный день по еде.
```

### 4.2. Быстрое переключение периода

Пользователь:

- нажимает кнопку `Следующий период` под уже показанным отчётом.

Система:

- перестраивает тот же отчёт для нового периода;
- не требует повторного ввода команды;
- циклически переключает предустановленные периоды;
- сохраняет ту же общую структуру ответа.

Используемые периоды:

- `8 дней`;
- `16 дней`;
- `32 дня`.

### 4.3. Просмотр заметных записей пищи

Пользователь:

- нажимает кнопку `Заметные записи пищи`.

Система:

- показывает отдельную детализацию по конкретным food entries за тот же период;
- при необходимости использует внутренний порог отбора;
- не требует, чтобы пользователь понимал, что такое percentile;
- строит сообщение только по одной метрике за раз;
- даёт кнопки `Следующая метрика` и `Закрыть`.

Ожидаемое направление ответа:

```text
Заметные записи пищи: 19.05.2026-25.05.2026
Метрика: калории
Доступно: [калории], белки, жиры

- 21.05 20:10 · бургер и картофель · 1 140 ккал
- 23.05 08:40 · завтрак в кафе · 920 ккал
- 24.05 22:15 · роллы · 880 ккал
```

### 4.4. Просмотр динамики

Пользователь:

- нажимает кнопку `Динамика`.

Система:

- показывает отдельное сообщение с динамикой по одной метрике;
- делит выбранный период на подпериоды по `4` дня;
- показывает подпериоды в хронологическом порядке;
- для каждого подпериода выводит среднее значение по текущей метрике;
- если данные есть, дописывает число дней с данными в формате `(N/4 дней)`;
- если данных нет, явно пишет `нет данных`;
- даёт кнопки `Следующая метрика` и `Закрыть`.

Ожидаемое направление ответа:

```text
Динамика: 10.05.2026-25.05.2026
Метрика: белки
Доступно: калории, [белки], жиры, углеводы

10.05-13.05: 98 г (3/4 дней)
14.05-17.05: 121 г (4/4 дней)
18.05-21.05: нет данных
22.05-25.05: 109 г (2/4 дней)
```

## 5. Рекомендуемая техническая рамка

### 5.1. Начинать стоит поверх уже существующего summary слоя

В проекте уже есть:

- дневные nutrition summary;
- water summary;
- goal snapshots;
- workout-related factual слой.

Следствие:

- первую версию периодного отчёта разумно строить как aggregation поверх существующих дневных/use-case слоёв;
- не нужно заранее вводить отдельную БД-модель периодных отчётов, пока не подтверждена реальная необходимость.

### 5.2. Нужен отдельный reporting/use-case boundary

Несмотря на возможность переиспользовать текущие daily summary, периодный отчёт не стоит собирать ad hoc прямо в handler.

Рекомендуемое направление:

- отдельный reporting use case или service boundary;
- отдельная структура результата period report;
- отдельный рендерер пользовательского текста.

Это упростит:

- тестирование правил расчёта;
- повторное использование для разных периодов;
- дальнейшее добавление детализаций и export/report действий.

### 5.3. Для period report нужен отдельный callback/state contract

Так как в UX появились:

- циклическое переключение периода;
- отдельное сообщение детализации;
- циклическое переключение метрик внутри детализации;
- отдельное сообщение динамики;
- циклическое переключение метрик внутри динамики;
- удаление сообщений по кнопке,

нужно заранее выделить отдельный callback/state contract для period report и его деталей, а не смешивать это с существующими callback-структурами ad hoc.

### 5.4. Настройка допуска может сначала жить как текущая пользовательская настройка

Есть открытый архитектурный вопрос: должен ли допуск к цели снапшотиться по дням так же, как снапшотятся сами goals.

Текущее рекомендуемое инкрементальное направление:

- goals продолжать брать из historical snapshots;
- допуск к цели на первом шаге читать из текущей пользовательской настройки;
- если позже потребуется строгая историческая воспроизводимость аналитики, обсуждать это отдельным шагом и, возможно, через ADR.

### 5.5. Percentile-настройка тоже должна быть оформлена как часть пользовательских настроек

Так как percentile-порог влияет на состав детализации, а не на фактические данные пользователя, на первом шаге его тоже разумно читать из текущих пользовательских настроек.

При этом:

- имя настройки и пользовательский текст должны быть понятны без статистического жаргона;
- внутренняя реализация может опираться на percentile, даже если пользовательский лейбл будет мягче.

## 6. Закрытые решения текущего этапа обсуждения

### 6.1. Дефолтный период `/report`

Согласовано:

- дефолтный период `/report` равен `8 дней`.

### 6.2. Как считать день с данными по еде

Согласовано:

- день с данными по еде считается, если в этот день есть любое количество записей еды.

Это не отменяет отдельного различия между:

- днём с данными по еде;
- полным днём по еде, пригодным для точного nutrition comparison.

### 6.3. Как считать заметные записи пищи

Согласовано:

- percentile-порог задаётся пользовательской настройкой;
- допустимый диапазон настройки: `70%`-`95%` с шагом `5%`;
- детализация открывается по одной метрике за раз;
- доступны только метрики, которые включены у пользователя и имеют записи в периоде;
- в списке показывается не больше `10` записей;
- у записи обязательно показывается дата.

### 6.4. Как считать динамику

Согласовано:

- динамика открывается отдельной кнопкой `Динамика`;
- базовый размер подпериода равен `4` дням;
- подпериоды показываются в хронологическом порядке;
- если в подпериоде нет данных по метрике, выводится `нет данных`;
- если данные есть, рядом со значением показывается `(N/4 дней)`;
- среднее в подпериоде считается по дням с данными внутри этого подпериода.

### 6.5. Где жить новым настройкам

Согласовано:

- новые настройки живут в `/settings`;
- допустимо изменить текущий порядок и форму кнопок в `settings`, если это делает UX понятнее.

### 6.6. Нужен ли ADR до реализации

Рекомендуемое решение:

- перед реализацией завести ADR.

Причины:

- меняется пользовательская модель настроек;
- вводятся как минимум две новые настройки;
- меняется правило интерпретации “день в цели”;
- появляется отдельный callback/state contract для report UX;
- нужно явно зафиксировать, какие правила считаются текущими пользовательскими настройками, а какие историческими фактами.
