# AGENTS.md

## Общие правила

- При подготовке описаний коммитов используй русский язык.
- Проект разрабатывается на Python.
- Основная база данных проекта - PostgreSQL.
- Приложение предполагается запускать через Docker.
- Развивай проект инкрементно: предпочитай решения, которые не мешают постепенно уточнять модель и схему БД.
- Для тестов используй `pytest`.
- При выборе инструментов для тестирования бота предпочитай совместимые с `aiogram` решения, а не самодельную инфраструктуру без необходимости.
- Секреты локальной разработки не хранятся в репозитории и не добавляются в `.venv`; проектный путь для них - sibling-каталог `../food_registry_bot_local/.env`.

## Цикл работы

- Работай короткими инкрементами: сначала понять задачу, затем внести минимальное полезное изменение и показать результат.
- Если изменение затрагивает доменную модель, API-контракт или схему БД, сначала явно сформулируй решение и при необходимости зафиксируй его в ADR.
- Не строй лишнее заранее: не добавляй абстракции, таблицы, конфиги и расширяемость без практической потребности текущего шага.
- Если пользователь просит доработку, которая зависит от другой ещё не реализованной целостной функциональности, явно обозначь эту зависимость и не приступай к реализации запрошенного изменения, пока не будет согласован или выполнен необходимый базовый этап.
- Каждый шаг по возможности должен оставлять проект в проверяемом состоянии.
- Если изменились сценарии, ограничения или принципы модели, обнови документацию в том же рабочем цикле.
- Если решение может заметно переусложнить архитектуру или плохо обратимо, сначала обсуди его, а не достраивай молча.
- Предпочитай простые и наблюдаемые решения, которые легко запускать и отлаживать в Docker и через прямую проверку данных в БД.

## Документация

- `README.md` должен описывать проект, его назначение, ключевые сценарии и архитектурные договорённости.
- `docs/development-workflow.md` фиксирует обязательный процесс разработки, правила работы с ветками и порядок релиза.
- Не добавляй в документацию статусные секции, roadmap, MVP-планы и другие процессные артефакты, если у них нет явной практической пользы и договорённости об их сопровождении.
- Избегай ритуалов без пользы: не предлагай и не создавай сущности, которые требуют регулярного обновления, но не помогают разработке или эксплуатации.
- Архитектурные решения, принципы модели данных и важные компромиссы фиксируй в `docs/adr/`, а не в виде временных заметок.

## Модель данных

- Источник истины для данных - база данных, а не внешние таблицы.
- Новые поддерживаемые метрики добавляются разработчиком в коде и через миграции.
- Пользователь может настраивать только то, какие из поддерживаемых метрик ему отслеживать.
- Исторические данные должны сохранять свой исходный смысл при изменении текущих настроек пользователя.
- Дневные цели должны фиксироваться как снимок настроек на конкретную дату, а не вычисляться только из текущего состояния профиля.

## Изменения схемы

- Перед существенными изменениями схемы БД или доменной модели сначала проверь, нужно ли зафиксировать решение в ADR.
- При проектировании миграций предпочитай простые и обратимые изменения.
